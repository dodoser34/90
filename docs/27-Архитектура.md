# Архитектура магазина: слои и сборка

Сервер K-Beauty | C-Health использует **послойную архитектуру**. HTTP-обработчики, правила входных данных, сервисы и работа с базой имеют отдельные каталоги. Оплата выделена в набор реализаций общего интерфейса. SQLAlchemy работает асинхронно; PostgreSQL используется на сервере, SQLite — для локального запуска и тестов.

## Сборка приложения

```text
app/main.py                 точка входа app.main:app
    └─ application.py       create_app(): FastAPI, middleware, CORS, роутеры, media
        ├─ lifecycle.py     настройки, локальная БД, администратор, закрытие engine
        ├─ core/            настройки, защита и очистка ввода
        └─ api/routers/     подключение обработчиков HTTP
```

`main.py` создаёт экземпляр через `create_app()`. Фабрика в `application.py` связывает слои. Жизненный цикл в `lifecycle.py` проверяет настройки, подготавливает локальную базу и администратора; после штатного завершения освобождает соединения. Прикладные сервисы не импортируют `main.py` или фабрику приложения.

Проверка состояния находится в `api/routers/health.py`: `GET /api/health` выполняет `SELECT 1`, возвращая 200 при доступной базе и 503 при ошибке соединения. Она не раскрывает текст ошибки базы пользователю.

## Разделение ответственности

| Каталог | Что меняется здесь | Пример |
|---|---|---|
| `api/` | HTTP-адреса, проверка прав, подготовка ответа | `api/routers/orders.py`, `api/deps.py` |
| `schemas/` | Типы и ограничения входных данных | `schemas/orders.py` |
| `services/` | Операции с письмами, оплатой и стартовым наполнением | `services/emails.py` |
| `db/` | Модели, ограничения, асинхронные сессии | `db/models.py`, `db/session.py` |
| `core/` | Общие настройки, криптография, лимиты, очистка | `core/config.py`, `core/middleware.py` |
| `migrations/` в `backend/` | История изменения схемы базы | Миграции Alembic |

Маршруты используют схемы, сервисы, базу и общие зависимости. Схемы не выполняют запросы к БД. Модели не знают об HTTP-маршрутах. Не следует переносить настройки магазина в обработчик отдельной страницы.

При оформлении заказа маршрут проверяет входные данные и права, читает товары из базы и сохраняет заказ; сервис оплаты выбирает способ оплаты. Текущая реализация не вводит отдельного слоя репозиториев или сервиса для каждого HTTP-метода.

## Расширение оплаты

В `services/payments/base.py` описан общий интерфейс. `cash.py`, `kaspi_transfer.py`, `sandbox.py` и `kaspi_pay.py` реализуют конкретные способы. Реестр в `services/payments/__init__.py` отвечает за выбор доступного способа по настройкам. Чтобы добавить провайдера, нужно реализовать его контракт, зарегистрировать метод и проверить создание заказа, инструкции оплаты, статусы и уведомления.

## Витрина и состояние браузера

Клиент использует `frontend/js/app.js` как загрузчик. Разделы сайта находятся в `js/pages/`, общее состояние — в `js/store/`, административный интерфейс — в `js/admin/`. Тексты вынесены в `frontend/texts/ru/`; адаптивные стили сгруппированы в `frontend/css/responsive/` по размеру устройства. Демо-режим и серверный режим подключаются через слой хранилища.

## Проверка после изменения

Из папки `backend` выполнить `.venv\Scripts\python -m pytest -q`. Тесты создают временную базу, подменяют отправку писем и внешние платёжные вызовы. При изменениях схемы данных дополнительно подготовить миграцию. Правила расширения всего проекта описаны в [главе 26](26-Разработка-и-поддержка-документации.md).

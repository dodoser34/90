# 27. Архитектура: как части магазина работают вместе

Эта глава нужна разработчику, чтобы выбрать правильное место для изменения и не смешать разные задачи в одном файле. Архитектура — способ разделить программу на понятные части. Для работы с товарами через админку эту главу можно пропустить.

У магазина две основные части: браузер показывает страницы и принимает действия, Python API проверяет запросы и работает с базой. На сервере используется PostgreSQL. Для простого локального запуска и части тестов — SQLite, база в одном файле.

## Пример: покупатель оформляет заказ

1. Страница в браузере собирает контакты, товары и количество.
2. Клиентский слой хранилища отправляет запрос API.
3. Схема проверяет поля: есть ли имя, допустимо ли количество, не слишком ли длинный текст.
4. Обработчик API проверяет вход пользователя, наличие товаров и остатки, считает сумму.
5. Сервис оплаты готовит нужные инструкции.
6. База сохраняет заказ и изменение остатков.
7. Сериализатор превращает запись базы в JSON-ответ, который браузер показывает покупателю.

Это разделение называется послойной архитектурой: у каждого слоя своя задача. В этом проекте часть правил заказа находится прямо в обработчике. Отдельного сервиса для каждого действия и отдельного слоя репозиториев нет.

## Как запускается API

Все пути следующей таблицы отсчитываются от `backend/`.

| Файл | Роль при запуске |
|---|---|
| `app/main.py` | Создаёт объект приложения; Uvicorn запускает его как `app.main:app` |
| `app/application.py` | Функция create_app собирает FastAPI: общие проверки, адреса API, CORS и раздачу фото |
| `app/lifecycle.py` | Проверяет настройки, при нужном локальном режиме готовит таблицы, создаёт/обновляет администратора; при завершении закрывает соединения |
| `app/api/routers/` | Содержит обработчики конкретных запросов |
| `app/core/` | Даёт общие настройки, защиту и очистку данных |

**Фабрика приложения** — это просто функция create_app, которая соединяет части и возвращает готовое приложение. Сервисы почты и оплаты не должны импортировать `main.py` или эту фабрику: им достаточно переданных данных и настроек.

При обычном Docker-запуске `entrypoint.sh` сначала проверяет конфигурацию, затем выполняет миграции, затем запускает Gunicorn с Uvicorn-процессами. Встроенное создание таблиц относится к локальной SQLite и не заменяет этот порядок на сервере.

## За что отвечает каждая папка

| Папка | Что здесь делать | Пример |
|---|---|---|
| `app/api/` | Задавать адрес запроса, проверять права и готовить ответ | `routers/orders.py`, `deps.py` |
| `app/schemas/` | Описывать допустимые поля и значения входящих данных | `orders.py` |
| `app/services/` | Выполнять операции почты, оплаты и начального наполнения | `emails.py`, `payments/` |
| `app/db/` | Описывать таблицы и подключение к базе | `models.py`, `session.py` |
| `app/core/` | Хранить общие настройки, криптографию, лимиты и очистку ввода | `config.py`, `middleware.py` |
| `migrations/` | Записывать историю изменений структуры базы | Файлы Alembic |

Схема проверяет форму запроса, но не выполняет SQL-запросы. Модель описывает таблицу, но не знает об адресе HTTP. Общая настройка читается из Settings, а не придумывается внутри обработчика одной страницы. Такое разделение помогает менять одну часть без лишних изменений остальных.

## Как устроена оплата

В `app/services/payments/base.py` описан общий интерфейс платёжного способа — какие действия он должен уметь. Конкретные реализации находятся в cash.py, kaspi_transfer.py, sandbox.py и kaspi_pay.py. Список в `payments/__init__.py` выбирает включённые и настроенные методы.

Для нового провайдера нужно реализовать его правила, добавить метод в список, подключить настройки и проверить создание заказа, инструкции, статусы и уведомления. Адрес и формат внешнего API подтверждаются по условиям провайдера. Наличие реализации в коде не подтверждает боевое подключение.

## Как устроена витрина

| Папка или файл | Роль |
|---|---|
| `frontend/js/app.js` | Загружает файлы в установленном порядке |
| `frontend/js/pages/` | Управляет отдельными страницами |
| `frontend/js/store/` | Даёт доступ к данным и выбирает локальную работу или API |
| `frontend/js/admin/` | Управляет административным интерфейсом |
| `frontend/texts/ru/` | Хранит надписи страниц |
| `frontend/css/responsive/` | Настраивает вид под размеры экрана и особенности устройства |

В локальном режиме данные остаются в браузере. При включённом API слой remote отправляет запросы серверу и обновляет локальные копии данных. Корзина и избранное при этом остаются в конкретном браузере. Демо добавляет свои примеры и поведение отдельным расширением.

## Что проверять после изменения

Из папки `backend` в Windows выполните:

```powershell
.venv\Scripts\python.exe -m pytest -q
```

Команда предполагает, что окружение и зависимости уже подготовлены. Тесты создают временную базу, заменяют отправку писем и внешние платёжные запросы. Они проверяют код без реального списания денег и реальной почтовой доставки. Команды остальных проверок находятся в [главе 16](16-Тесты-и-проверка-качества.md).

Если менялась структура таблиц, подготовьте миграцию и проверьте её на отдельной базе. Если менялся интерфейс, просмотрите нужное действие в браузере. Подробный порядок разработки — [глава 26](26-Разработка-и-поддержка-документации.md).

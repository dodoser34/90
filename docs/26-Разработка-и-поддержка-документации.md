# 26. Как изменять проект и поддерживать документацию

Этот раздел предназначен тому, кто будет продолжать разработку. Для обычного управления магазином достаточно [11. Админ-панель](11-Админ-панель.md) и [12. Частые правки](12-Тексты-фото-и-частые-правки.md).

## Перед первой правкой

Запустите выбранный режим по [2](02-Как-запустить.md), определите источник данных и проследите затрагиваемый сценарий по [22](22-Карта-папок-и-файлов.md). Установите зависимости в отдельное окружение, а не в системный Python. Исходники фронтенда правятся в frontend, а не в `.public/`.

README и docs описывают состояние репозитория, а не подтверждённое состояние чужого сервера. Секреты и реальные данные покупателей для документации не нужны.

## Какие файлы затрагивает задача

| Задача | Где править | Что проверить |
|---|---|---|
| Надпись, title, описание страницы | texts/ru/<раздел>.js | Значение ключа, переносы, mobile |
| Цвет, шрифт, ширина | css/base/variables.css и профильный CSS | Контраст, фокус, телефон/планшет/desktop |
| Логика корзины | js/store/cart.js и компоненты | JS-тесты, недоступные товары, количество |
| Поле товара | Форма админки, store/products, schemas/catalog, serializer; колонка модели при необходимости | Сохранение/чтение API, старые товары, локальный режим |
| Новая страница | HTML + texts + CSS + JS и запись PAGES в app.js | Пути data-base, загрузка, ссылки и доступ |
| Новая таблица/колонка | models.py + миграция + schemas/роутеры | SQLite/PostgreSQL, upgrade/check, совместимость данных |
| Новый адрес API | Router + schema + права + remote.js при использовании UI | Токен, роль, неверные данные, ошибки |
| Настройка сервера | Settings + шаблон .env + Compose/Render, если нужно | Default, production problems, документация |
| Платёжный метод | services/payments, реестр, Settings и webhook при необходимости | Контракт провайдера, подпись, сумма, повторы, отказ |

## Добавить страницу

Используйте каркас существующей страницы того же уровня вложенности. Назначьте уникальный data-page, укажите правильный data-base. Добавьте запись PAGES в app.js: сначала тексты/вспомогательные файлы, потом контроллер. Страничная логика должна учитывать `app:ready` и существующую схему событий. CSS подключите в main.css, адаптивные правила — через responsive/index.css. Добавьте страницу в документацию и навигацию при необходимости.

Для нового языка мало скопировать texts/ru: нужно заполнить все используемые ключи, сменить lang в соответствующих HTML, проверить форматирование и текст серверных ошибок. Готового переключателя языка в текущем проекте нет.

## Изменить модель базы

Команды выполняются из backend с активным окружением и **отдельной базой разработки**, управляемой Alembic:

```bash
alembic upgrade head
alembic revision --autogenerate -m "add_product_field"
alembic upgrade head
alembic check
```

Перед генерацией измените models.py. Созданный файл обязательно прочитайте: autogenerate не знает, является ли удаление/добавление колонки переименованием, и не разрабатывает безопасную миграцию данных за автора. Dev-база, созданная create_all, не обязательно имеет историю Alembic; для такого процесса удобнее новая отдельная база с миграциями.

В CI проверяются upgrade, check и downgrade base на одноразовом PostgreSQL. Эти действия не являются инструкцией стирать рабочую схему. Если добавили обязательное поле к существующим строкам, продумайте начальное значение/заполнение и порядок развёртывания.

## Проверить изменение

Команды и состав тестов — [16](16-Тесты-и-проверка-качества.md). Выбирайте проверки по затронутому поведению. Исправление серверных расчётов требует API/сценарных тестов; правка текстов — проверки ключей и просмотра страницы. Автотесты логики JS не заменяют проверку отображения и взаимодействия в браузере.

Для ручного просмотра используйте DevTools: Console показывает ошибки, Network — неудачные загрузки и API, Application — localStorage, режим устройств — адаптивность. Запишите воспроизводимый сценарий и результат; не объявляйте все размеры/браузеры проверенными без выполненного запуска.

## Что обновлять в документации

| Изменение исходника | Глава документации |
|---|---|
| Новый каталог, модуль, страница | 3, 4/6/7, 22 |
| Зависимость или версия runtime | 7 и 20 |
| Конфигурационный файл, workflow | 16 и 21 |
| Переменная Settings, Compose | 13 и 23 |
| API-поле, статус, маршрут, права | 7 и 24 |
| Сборка, инфраструктура, backup | 13, 14 и 25 |
| Пользовательская функция | 1, 11/12, FAQ 17 |

Сначала описывайте реализованное поведение, затем ограничения. Например: «в коде есть адаптер с таким контрактом; соединение с боевым провайдером не подтверждено». Не заменяйте это обещанием, что подключение уже работает.

## Как читать команды

`bash` — команды Linux/macOS и VPS. `powershell` — Windows. Для Python окружения пути отличаются: `backend/.venv/Scripts/python.exe` и `backend/.venv/bin/python`. Команды с `cd backend` требуют соответствующей рабочей папки. `…` в таблице обозначает сокращение, его нельзя буквально вставлять вместо полной команды.

Тестовые адреса `example.com`, `example.kz`, ID `p-example` и `<домен>` — заполнители, а не рабочие значения. Переменная API_URL публична, SECRET_KEY/пароли/токены — нет. Секреты передаются через локальное окружение, `.env` или панель хостинга.

## Границы проекта, которые нужно помнить

Проект — многостраничная витрина с клиентским рендерингом и FastAPI. Нет общей синхронизации корзины между устройствами, серверной пагинации каталога, общей Redis-базы лимитов, автоматического возврата денег, полноценного браузерного E2E-workflow или гарантии обновления без простоя. Это описание текущего устройства, а не список обязательных доработок для каждой правки.

## Финальная проверка документации

Проверить относительные ссылки, существование названных файлов, соответствие версий requirements, наличие всех Settings в справочнике, имена команд и папок. Команда `git diff --check` выявляет часть ошибок пробелов в отслеживаемом diff. Время, количество тестов и сведения о внешних тарифах не закрепляйте как вечные факты.

Если выполнялась проверка, укажите дату, команду, окружение и результат. Если не выполнялась — так и напишите. Не переносите старое «все тесты проходят» на новый код автоматически.

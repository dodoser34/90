# 24. API: адреса запросов и данные

Эта глава нужна разработчику, который связывает сайт с сервером или ищет причину ошибки запроса. Обычный пользователь управляет магазином через страницы и админку; отправлять эти запросы вручную ему не требуется.

**API** — набор адресов для получения и изменения данных. Например, браузер отправляет запрос «создай заказ», а сервер отвечает номером, составом и суммой. **HTTP** задаёт способ обмена запросами. **JSON** — текстовый формат данных внутри запроса и ответа.

Все адреса начинаются с `/api`. Код запросов находится в `backend/app/api/routers/`, правила полей — в `backend/app/schemas/`, преобразование записей базы в ответы — в `backend/app/api/serializers.py`.

Локально интерактивное описание открывается по адресу `http://localhost:8000/api/docs`, его JSON-схема — `/api/openapi.json`. В production они по умолчанию выключены. Уведомление Kaspi не включено в эту схему и описано отдельно ниже.

## Как прочитать запрос

```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json

{"email":"buyer@example.com","password":"пароль локального аккаунта"}
```

Этот пример означает: отправить email и пароль в адрес входа. Учебный адрес и пароль нужно заменить данными своего локального аккаунта. По умолчанию локальный сервер находится на `http://localhost:8000`.

| Метод | Что обычно делает |
|---|---|
| GET | Читает данные |
| POST | Создаёт запись или выполняет действие |
| PUT | Сохраняет переданное состояние целиком |
| PATCH | Меняет отдельные поля |
| DELETE | Удаляет запись |

После входа сервер возвращает `token`. Для защищённого запроса клиент передаёт заголовок `Authorization: Bearer <token>`. Это случайный ключ сессии, а не JWT. В базе хранится его SHA-256-отпечаток и срок действия, в браузере исходный токен хранится в localStorage.

Параметры адреса идут после `?`, например `/api/products?all=1`. Текст параметров нужно кодировать через URLSearchParams или encodeURIComponent. В JSON-запросе нужен `Content-Type: application/json`. В текущем клиенте эту работу выполняет `request()` из `frontend/js/store/remote.js`.

В таблицах «пользователь» означает вошедший и допущенный сервером аккаунт. «Админ» — дополнительная проверка роли admin. Запись в фигурных скобках, например `{product_id}`, заменяется настоящим ID. Знак `?` после имени поля означает, что поле необязательное; сам знак в JSON не добавляется.

## Аккаунт и вход

| Метод и адрес | Поля | Результат и доступ |
|---|---|---|
| `POST /api/auth/register` | name, email, password | Без входа: создаёт неподтверждённый аккаунт и отправляет код |
| `POST /api/auth/verify` | email, code | Без входа: подтверждает почту, возвращает токен и пользователя |
| `POST /api/auth/resend` | email | Без входа: повторно запрашивает письмо подтверждения |
| `POST /api/auth/login` | email, password | Без входа: после проверки возвращает токен и пользователя |
| `POST /api/auth/logout` | Нет | Завершает текущую сессию, если токен передан; работает и без действующей сессии |
| `POST /api/auth/logout/all` | Нет | Пользователь: завершает все свои сессии |
| `GET /api/auth/me` | Нет | Пользователь: получает свой профиль |
| `PATCH /api/auth/me` | name?, phone? | Пользователь: меняет свой профиль |
| `DELETE /api/auth/me` | password | Пользователь: удаляет свой аккаунт; серверного администратора удалить так нельзя |
| `POST /api/auth/password/change` | old, new | Пользователь: меняет пароль и завершает остальные сессии |
| `POST /api/auth/password/forgot` | email | Без входа: запрашивает код сброса |
| `POST /api/auth/password/reset` | email, code, password | Без входа: сбрасывает пароль по коду и возвращает новую сессию |

Почтовый код состоит из 6 цифр. Имя — от 2 до 80 символов. Email проверяется на формат почтового адреса. Пароль в схеме ограничен 200 символами, а правила минимальной длины и сложности дополнительно проверяются в `core/security.py`. Поэтому `min_length=1` в схеме не разрешает пароль из одной буквы. Телефон профиля — до 32 символов: цифры, пробелы, скобки, `+` и `-`.

Успешный ответ `sent` не доказывает существование адреса: некоторые запросы возвращают общий ответ. Вход по коду без пароля и Google OAuth в текущих маршрутах отсутствуют.

## Категории, товары и фотографии

| Метод и адрес | Данные | Доступ и результат |
|---|---|---|
| `GET /api/categories` | Нет | Всем: категории и подкатегории |
| `PUT /api/categories` | Полный список категорий с subs | Админ: сохраняет весь список |
| `GET /api/products` | `all=1`, если нужны скрытые | Всем: опубликованные; админу с параметром — также скрытые |
| `GET /api/products/{key}` | В адресе ID или slug | Всем: доступный товар; скрытый виден только админу |
| `POST /api/products` | ProductIn | Админ: создаёт товар, HTTP 201 |
| `PUT /api/products/{product_id}` | ProductIn | Админ: сохраняет полное состояние товара |
| `DELETE /api/products/{product_id}` | Нет | Админ: удаляет товар |
| `POST /api/uploads` | data, folder | Админ: загружает фото, HTTP 201; ответ с полем url |

**Категория.** Поля `id` и `name` обязательны. ID — 1–60 строчных латинских букв, цифр и дефисов, первый символ — буква или цифра. Имя — 1–80 символов. `icon` — до 32 символов, по умолчанию `leaf`. В `subs` до 50 подкатегорий с полями id/name по тем же правилам. ID категорий не должны повторяться. Удалить категорию с товарами нельзя: сначала их переносят.

**Товар, ProductIn.** Это название схемы, а не поле JSON.

| Поле | Ограничение или значение |
|---|---|
| name | Обязательно, 1–160 символов |
| slug | До 120 символов на входе; сервер превращает в короткую часть адреса |
| brand | До 80 символов |
| category, sub | До 60 символов каждое; заданная категория должна существовать |
| status | `published` — опубликован; `hidden` — скрыт |
| price, oldPrice | Целые тенге, 0–100000000; oldPrice необязательно |
| stock | Остаток 0–1000000 |
| images | До 20 безопасных адресов фотографий, каждый до 500 символов |

При пустом price или stock используется 0. Поле oldPrice сохраняется в колонку old_price; нулевая старая цена трактуется как отсутствие. Slug нормализуется, а при совпадении получает суффикс. Дополнительные поля товара разрешены: их строки очищаются, вложенность ограничивается, сериализованный набор ограничен 200000 символами. Основные поля хранятся отдельными колонками базы.

При PUT передавайте весь редактируемый товар. Отсутствующее поле с исходным значением может сброситься к нему; это не частичная правка одного свойства.

**Загрузка фото.** `data` содержит строку вида `data:image/png;base64,…`, `folder` — `products` или `site`, по умолчанию `products`. Используется JSON, а не обычная форма multipart/form-data. Схема ограничивает строку data 20000000 символами. Отдельно проверяется размер файла по `MAX_UPLOAD_MB`, по умолчанию 8 МБ.

Сервер принимает JPG, PNG и WEBP, проверяет base64 и начальные байты формата, назначает случайное имя. Это не полное открытие и исследование изображения. Загрузка файла и сохранение адреса в товаре — два разных запроса.

## Заказы и способы оплаты

| Метод и адрес | Что делает | Доступ |
|---|---|---|
| `GET /api/payments/methods` | Отдаёт включённые и настроенные способы оплаты | Всем |
| `POST /api/orders` | Создаёт заказ по OrderIn, HTTP 201 | Пользователь |
| `GET /api/orders/my` | Отдаёт свои заказы | Пользователь |
| `GET /api/admin/orders` | Отдаёт все заказы | Админ |
| `PATCH /api/admin/orders/{order_id}` | Меняет status и/или paymentStatus | Админ |
| `DELETE /api/admin/orders/{order_id}` | Удаляет запись заказа | Админ |
| `POST /api/payments/sandbox/{order_id}` | Имитирует оплату или отмену | Владелец заказа |
| `POST /api/payments/kaspi/webhook` | Принимает внешнее уведомление об оплате | Проверка HMAC-подписи; нужен включённый kaspi_pay |

Пример OrderIn для локального теста. Вместо `p-example` нужен ID существующего опубликованного товара с остатком:

```json
{
  "name": "Тестовый покупатель",
  "phone": "+7 (701) 123-45-67",
  "email": "buyer@example.com",
  "delivery": "pickup",
  "city": "",
  "address": "",
  "comment": "Учебный заказ",
  "payment": "cash",
  "items": [{"id": "p-example", "qty": 1}]
}
```

| Поле заказа | Правило |
|---|---|
| name | 2–80 символов |
| phone | 10–32 символа: цифры, пробелы, скобки, `+` и `-` |
| email | Необязательно, до 254 символов; если пусто, используется почта аккаунта |
| delivery | `courier` — курьер; `kazakhstan` — доставка по стране; `pickup` — самовывоз |
| deliveryTitle | Необязательная подпись до 120 символов |
| city, address | До 80 и 200 символов; обязательны для courier/kazakhstan |
| comment | До 1000 символов |
| payment | Код включённого способа, до 24 строчных латинских букв и `_` |
| items | 1–50 строк; ID товара 1–40 символов, qty — количество 1–99 |

Браузер передаёт контакты, товары, количество и выбранные способы. Сервер сам назначает пользователя, статус, цены и итог. Он пропускает отсутствующие, скрытые и закончившиеся товары и уменьшает количество до доступного остатка. Если не осталось ни одного доступного товара, возвращает HTTP 409. Успешно созданный заказ может отличаться от исходной корзины — проверяйте его ответ.

В PostgreSQL остатки блокируются и меняются вместе с заказом в одной транзакции: связанном наборе изменений базы. SQLite не повторяет все гарантии одновременной работы PostgreSQL.

Ответ заказа включает id, number, userId, status, name, phone, email, delivery, deliveryTitle, city, address, comment, payment, paymentTitle, paymentStatus, paid, items, subtotal, deliveryPrice, total, createdAt. Если нужны действия оплаты, добавляется paymentInstructions. Суммы — целые тенге. Покупательский номер начинается с 1001; внутренний ID выглядит как `o-…`.

| Поле | Допустимые значения |
|---|---|
| status | `new` — новый; `processing` — в работе; `shipped` — отправлен; `done` — завершён; `cancelled` — отменён |
| paymentStatus | `pending` — ожидается действие; `awaiting` — ожидается оплата; `paid` — оплачен; `failed` — неуспешно; `refunded` — отмечен возврат |

Перевод в cancelled возвращает остатки. Восстановление отменённого заказа заново проверяет и списывает их. Удаление записи заказа не возвращает остатки. `refunded` только записывает статус: автоматического возврата денег через банк нет.

Для POST /orders нет общего ключа защиты от повторного создания. Если после отправки оборвалась сеть, сначала проверьте «Мои заказы». Повторный запрос может создать ещё один заказ.

## Тестовая оплата

Sandbox — имитация без списания денег. Принимается SandboxPayIn: `action` — pay или cancel, `card` — до 23 символов, `expiry` — MM/YY, `cvc` — до 4 цифр. Для тестовой карты дополнительно проверяются номер, срок и CVC; действие cancel используется тестовым Kaspi. Примеры — в [главе 10](10-Оплата.md).

Оплата доступна владельцу заказа с включённым тестовым способом. Оплаченный, отмеченный возвращённым или отменённый заказ повторно оплатить этим запросом нельзя. Реальные реквизиты карты в тестовую форму не вводят.

## Внешнее уведомление Kaspi

Webhook — запрос, который платёжный сервис сам отправляет магазину. Реализованный код ждёт `X-Signature`: HMAC-SHA256 в шестнадцатеричном виде от исходного тела запроса с ключом `KASPI_WEBHOOK_SECRET`.

В JSON ожидаются orderId, status и amount. Статусы paid/success/completed считаются успешными. Сумма — целое неотрицательное число или строка цифр, совпадающая с total заказа. Для уже paid/refunded повтор возвращает ok. Неуспешный статус отмечает failed.

Это описание контракта текущего кода. Его нужно подтвердить у провайдера перед боевым подключением; само наличие маршрута не подтверждает работающую банковскую интеграцию.

## Отзывы

| Метод и адрес | Поля или параметры | Доступ |
|---|---|---|
| `GET /api/reviews` | productId?, all?, voter? | Всем опубликованные; автору также свои скрытые, админу с all — все |
| `POST /api/products/{product_id}/reviews` | rating, text, title?, pros?, cons?, recommend?, period?, voter? | Пользователь: создаёт или меняет свой отзыв |
| `POST /api/reviews/{review_id}/vote` | voter | Пользователь или гость с идентификатором voter |
| `PATCH /api/reviews/{review_id}/status` | status: published/hidden | Админ |
| `POST /api/reviews/{review_id}/reply` | text | Админ: ответ магазина, пустая строка удаляет ответ |
| `DELETE /api/reviews/{review_id}` | Нет | Автор или админ |

rating — оценка 1–5, text — 20–1500 символов, title — до 80, pros/cons — до 200 каждый. recommend по умолчанию true. period принимает пустую строку, lt1, 1to3, gt3. voter — до 64 букв, цифр, `_` и `-`. productId в фильтре — до 40 символов. Ответ магазина — до 1500 символов.

Имя автора сервер берёт из аккаунта, даже если клиент прислал name. Ответ сохранения имеет поля updated и review. Отметка verified означает, что товар есть в неотменённом заказе пользователя; отдельного подтверждения оплаты или получения для неё нет. Гостевой voter находится в браузере и не гарантирует, что каждый голос принадлежит отдельному человеку.

## Сайт, пользователи и состояние сервера

| Метод и адрес | Что делает | Доступ |
|---|---|---|
| `GET /api/site` | Отдаёт замены фотографий в sitePhotos | Всем |
| `PUT /api/site/photos` | Сохраняет index 0–5 и url до 500 символов; пустой url возвращает исходное фото | Админ |
| `GET /api/admin/users` | Отдаёт список пользователей | Админ |
| `PATCH /api/admin/users/{user_id}` | blocked? — блокировка; name? — имя 2–80 символов | Админ; себя заблокировать нельзя |
| `DELETE /api/admin/users/{user_id}` | Удаляет пользователя | Админ; администратора удалить нельзя |
| `GET /api/bootstrap` | Отдаёт начальный набор данных, voter? | Набор зависит от входа |
| `GET /api/admin/system` | Показывает режим, заполнение почты/оплаты и проблемы настроек без секретов | Админ |
| `GET /api/health` | Проверяет базу запросом SELECT 1 | Всем: HTTP 200 и status=ok или HTTP 503 при ошибке |

Bootstrap объединяет user, categories, products, reviews, orders, users, site, payments, config. Гостю orders/users приходят пустыми. Покупатель получает свои заказы и собственную запись пользователя. Админ получает полный набор. config содержит freeShippingFrom и courierPrice. Пароли, токены и почтовые коды сериализатор пользователя не отдаёт.

## Как читать ошибки

| HTTP-код | Что обычно означает |
|---|---|
| 400 | Действие невозможно или уведомление имеет неверный формат |
| 401 | Нужен вход либо сессия закончилась |
| 402 | Тестовая оплата отклонена |
| 403 | Нет прав, аккаунт заблокирован или подпись неверная |
| 404 | Запись не найдена либо скрыта от этого пользователя |
| 409 | Конфликт: остатки, статус, занятая категория или сумма |
| 413 | Слишком большой запрос или файл |
| 422 | Поля не прошли проверку |
| 429 | Слишком много попыток; Retry-After может сообщать время ожидания |
| 500 | Непредвиденная ошибка сервера |
| 502 / 503 | Недоступен внешний сервис или база |

Обычно сообщение приходит в поле detail. Проверка Pydantic может вернуть список ошибок полей, а отдельный обработчик — объект с message/code. Клиент учитывает эти варианты. Nginx может отклонить запрос раньше API и вернуть другой формат.

Успешный health доказывает, что доступна база. Он не проверяет доставку писем, оплату, резервные копии и все действия магазина.

## Что API пока не делает

Каталог фильтруется и разбивается на страницы в браузере: сервер не выдаёт эти списки отдельными порциями. Bootstrap и ряд других адресов возвращают большие наборы целиком. Корзина и избранное не синхронизируются между устройствами. Постоянного WebSocket-соединения для мгновенных обновлений нет; данные обновляются повторным запросом или перезагрузкой. При заметном росте каталога эти части потребуют развития.

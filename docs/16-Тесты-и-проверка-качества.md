# 16. Тесты и проверка качества

**Тест** — программа, которая проверяет ожидаемый результат. Например, сервер должен рассчитывать заказ по своей цене, даже если браузер прислал подменённые данные. Наличие теста и его успешное выполнение — разные факты: результат относится к конкретному запуску.

## Наборы проверок

| Набор | Файлы | Что проверяет |
|---|---|---|
| API | `backend/tests/test_api.py` | Аккаунты, каталог, заказы, отзывы, фото |
| Безопасность | `backend/tests/test_security.py` | Права, ошибки ввода, лимиты, заголовки, загрузки и секреты |
| Валидация | `backend/tests/test_validation_cases.py` | Границы полей и неправильные значения |
| Каталог | `backend/tests/test_catalog_cases.py` | Категории, slug, фото и ограничения API |
| База | `backend/tests/test_database_cases.py` | CHECK, уникальность, связи, удаление, откат |
| Заказы | `backend/tests/test_order_scenarios.py` | Доставка, остатки, отмена и доступ |
| Sandbox | `backend/tests/test_sandbox_payments.py` | Имитация карты/Kaspi, отказ и повторная оплата |
| Платёжный контракт | `backend/tests/test_payment_contract.py` | Разбор webhook, HMAC и целые суммы; без реального провайдера |
| Настройки | `backend/tests/test_readiness.py` | Проверки готовности и отказ production без настроек |
| Фронтенд | `tests/frontend/utils.test.cjs`, `store.test.cjs`, `catalog.test.cjs` | Помощники, localStorage, корзина, избранное и фильтры |
| Публичная сборка | `tests/general/test_public_build.py` | Разрешённый состав, API URL, владение результатом, CSS и пути |
| Демо | `demo/tests/test_ecosystem.py` | Изоляция, расширение, фотографии и версии ассетов |

Параметризация создаёт несколько тестовых случаев из одной функции. Точное число показывает pytest, а не подсчёт имён функций. Корневой pytest.ini выбирает только tests/general; backend имеет отдельную конфигурацию.

## Подготовка

Нужны Python 3.11 и Node.js 20 — такие версии заданы CI. Из корня проекта, Windows PowerShell:

```powershell
python -m venv backend/.venv
backend/.venv/Scripts/python.exe -m pip install -r backend/requirements-dev.txt
backend/.venv/Scripts/python.exe -m pip check
```

На Linux/macOS интерпретатор окружения находится в `backend/.venv/bin/python`. Для Python-проверок только сборки/демо CI устанавливает `pytest==8.3.4 pytest-asyncio==0.24.0`; backend-пакеты этим наборам не требуются.

## Команды запуска

Из корня проекта, PowerShell:

```powershell
node --test tests/frontend/*.test.cjs
backend/.venv/Scripts/python.exe -m pytest tests/general -q
backend/.venv/Scripts/python.exe -m pytest demo/tests -q
```

Backend — из своей папки:

```powershell
cd backend
.venv/Scripts/python.exe -m pytest -q
```

Выбрать один сценарий: `python -m pytest tests/test_order_scenarios.py -q` из backend с нужным Python. Посмотреть сбор тестов без выполнения: `python -m pytest --collect-only -q`. Зависимости всё равно должны быть установлены: conftest импортирует приложение.

Проверка синтаксиса JS на Windows:

```powershell
Get-ChildItem frontend -Recurse -Filter *.js | ForEach-Object {
  node --check $_.FullName
  if ($LASTEXITCODE -ne 0) { throw "Ошибка синтаксиса: $($_.FullName)" }
}
```

Она не запускает код в браузере и не проверяет существование всех runtime-объектов.

## Как изолированы данные

JS-тесты используют node:test, assert и VM-контекст из helpers.cjs с ограниченной имитацией DOM/localStorage. Это проверка логики, а не настоящий Chrome.

Тесты сборки используют временные копии, не рабочую `.public/`. Backend conftest выбирает временную SQLite либо TEST_DATABASE_URL, удаляет/создаёт таблицы перед сценариями, очищает лимиты, создаёт администратора и подменяет отправку писем. HTTPX обращается к приложению через ASGITransport без реального сетевого сервера. Платёжные вызовы имитируются.

**TEST_DATABASE_URL должен вести только в отдельную одноразовую тестовую базу.** Фикстура выполняет drop_all. Рабочую базу или локальную базу с нужными заказами сюда не подключают.

## Автоматические проверки GitHub

backend.yml запускает матрицу SQLite/PostgreSQL; на PostgreSQL проверяет upgrade head, alembic check и downgrade base, затем тесты и ожидаемый отказ настроек production. checks.yml проверяет синтаксис JS, JS-логику, публичную и опциональную демо-сборку. pages.yml публикует демо по своим условиям.

Запуски зависят от paths/ветки/события: изменение только docs не обязательно вызывает CI. Детали — [21](21-Конфигурационные-файлы.md). Настроенного workflow с полноценными браузерными E2E-тестами и отчётом покрытия нет.

Первые Python-запуски в системной временной папке получили WinError 5 при переименовании результата сборки. Повтор с временными папками внутри разрешённого workspace прошёл. Для такого повторения сначала создайте родительскую папку: `New-Item -ItemType Directory -Path .pytest-tmp -Force`.

Системное Python-окружение отличалось от закреплённого CI: pytest 9.1.1 и без pytest-asyncio. Оно выдало предупреждение Unknown config option: asyncio_default_fixture_loop_scope. Для штатных проверок используйте requirements-dev.txt; эта запись не утверждает успешный полный прогон в закреплённом окружении.

Результаты не подтверждают боевую SMTP/платёжную интеграцию, внешний хостинг, отсутствие всех уязвимостей или отображение на всех устройствах.

## Ручная проверка в браузере

Запустите серверный режим по [2](02-Как-запустить.md). Добавьте товар в админке либо отдельно заполните локальные демо-данные. Проверьте гостевой каталог и корзину, регистрацию/код, оформление, тестовую оплату, просмотр заказа администратором, отмену с возвратом остатка и закрытый доступ без сессии.

Повторите затронутые страницы на телефоне и desktop: отсутствие горизонтальной прокрутки, доступность полей и кнопок, клавиатура/Esc, уменьшенное движение. В Console не должно быть необработанных ошибок, в Network — неожиданных 404/500. Для CSS сравните исходники и публичную сборку. Результат записывайте с датой, браузером и размером окна.

# 25. Сборка, deploy и сопровождение

**Сборка** готовит файлы для публикации. **Deploy (развёртывание)** размещает приложение и запускает его в выбранной среде. В этом проекте Python-сборщик готовит фронтенд, Docker упаковывает API, Compose соединяет сервисы. Первая публикация пошагово — [13](13-Публикация-на-сервере.md) и [14](14-Запуск-за-час.md).

## Три режима и их результаты

| Режим | Что запускать / собирать | Где результат |
|---|---|---|
| Разработка витрины | `python deploy/serve_frontend.py` | Исходная папка frontend, localhost:5174 |
| Демо | `python demo/serve.py` либо `python demo/build.py` | demo/.public, просмотр на localhost:5175 |
| Публичная витрина | `python deploy/prepare_frontend.py` | .public в корне |
| Production API | Dockerfile + entrypoint | Образ backend и контейнер |

Node.js не собирает витрину: он нужен для JS-проверок. Изменение frontend/env.js не заменяет настройку backend и CORS.

## Что делает `prepare_frontend.py`

1. Проверяет исходную папку frontend и безопасность пути результата.
2. Создаёт временную staging-папку в корне проекта.
3. Копирует только разрешённые корневые файлы и типы файлов из pages, admin, css, js, texts, assets.
4. Исключает скрытые/служебные папки, symlink, private, tests, credentials, exports, backups, временные и тестовые файлы по правилам сборщика.
5. Объединяет локальные CSS-импорты верхнеуровневых файлов css/*.css, сохраняя порядок и пересчитывая относительные url(). Это объединение, а не минификация JS/CSS.
6. При `--api-url-from-env VARIABLE` проверяет публичный URL из указанной переменной и записывает env.js. Запрещены учётные данные, query и fragment; относительный адрес должен начинаться с одного `/`.
7. Повторно проверяет результат, заменяет свою `.public/` и записывает маркер `.public-build.json`.

Разрешённые корневые имена включают index.html, 404.html, env.js, .nojekyll, robots.txt, sitemap.xml и favicon. Это список допуска, а не утверждение, что все эти файлы уже существуют. Сборщик не генерирует sitemap или robots автоматически.

Если непустая `.public/` создана другим инструментом и нет правильного маркера, сборка откажется её заменять. Выясните назначение папки; не создавайте маркер вручную ради обхода проверки. Замена результата включает удаление старой папки, поэтому не является гарантированным обновлением без перерыва обслуживания.

Пример публичного API при сборке, PowerShell из корня:

```powershell
$env:API_URL = 'https://api.example.kz/api'
python deploy/prepare_frontend.py --api-url-from-env API_URL
```

В Docker-схеме общий домен использует deploy/env.js с `/api`: этот файл монтируется поверх env.js собранной витрины. На Render адрес записывает build command из render.yaml. На Pages демо использует пустой API и собственное расширение.

## Контейнеры, сети, данные

| Сервис | Роль | Постоянные данные |
|---|---|---|
| db | PostgreSQL 16, внутренний доступ | Named volume pgdata |
| backend | Проверка Settings → миграции → Gunicorn/Uvicorn | Named volume media; .public видна для seed только для чтения |
| web | Nginx, наружу 80/443 | Читает .public, media, сертификаты |
| certbot | Периодическая попытка продления | letsencrypt, certbot-www |
| certbot-init | Однократное получение сертификата, профиль init | letsencrypt |
| backup | pg_dump и архив media, очистка старых копий | deploy/backups на хосте |

Внешние порты базы и API не публикуются Compose. `expose: 8000` описывает внутренний порт, не открывает его в интернете. Backend входит во внутреннюю и публичную сети для доступа к базе и внешним сервисам. Certbot-init требует свободного 80 порта; web запускается после первичного получения сертификата.

`restart: unless-stopped` задаёт перезапуск контейнера; healthcheck показывает готовность сервиса, но сам по себе не гарантирует автоматический ремонт unhealthy-контейнера. Backend ждёт health базы, web имеет обычный depends_on без ожидания полной готовности API.

## Nginx по шагам

HTTP-запрос к домену перенаправляется на HTTPS, кроме ACME-пути. `www` приводится к основному домену. Неизвестные Host отсекаются default server.

| Путь | Куда идёт |
|---|---|
| `/api/…` | В backend:8000 с сохранением `/api` |
| `/media/…` | В volume media через alias |
| `/env.js` | Публичная настройка без кеша |
| HTML/CSS/JS/картинки | В `.public/` |
| Несуществующий файл | HTTP 404 с пользовательской 404.html |
| Скрытые/запрещённые служебные расширения | HTTP 404 |

Статические ассеты кешируются до 7 дней, media — до 30 дней. Для обновления используются версии `?v=…` у HTML-подключений и `VERSION` загрузчика; демо вычисляет версию по содержимому автоматически. Production-сборщик такой отпечаток JS/HTML автоматически не назначает. После смены CSS-импортов для прямого просмотра исходников учитывайте также их версии.

## Обновление существующего сервера

Все команды ниже — Bash на VPS из корня проекта. Сначала сохраните копию базы и media по [13](13-Публикация-на-сервере.md), зафиксируйте текущий commit и прочитайте изменения миграций. Развёртывание может прервать активные запросы.

```bash
git rev-parse HEAD
git pull --ff-only
python3 deploy/prepare_frontend.py
docker compose --env-file deploy/.env -f deploy/docker-compose.yml config --quiet
docker compose --env-file deploy/.env -f deploy/docker-compose.yml build backend
docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm --no-deps backend python -m app.cli check
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d
docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps
```

Затем проверьте HTTPS, `/api/health`, вход, каталог, фото и существующие заказы. Если менялись nginx-конфиги, проверьте их и примените reload; при смене окружения/DOMAIN пересоздайте web, чтобы шаблон сгенерировался заново:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec web nginx -t
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec web nginx -s reload
```

Backend entrypoint применяет миграции при старте. Автоприменение не доказывает, что любая будущая миграция без потерь: проверять её SQL и резервную копию нужно до запуска.

## Диагностика

| Симптом | Проверка и смысл |
|---|---|
| Процесс не запускается | `… logs --tail=100 backend`: типы Settings, production problems, права media, миграции |
| HTTP 502 от Nginx | Журналы web/backend; работает ли backend и слушает ли 8000 |
| HTTP 503 от health | Соединение с БД и состояние db |
| Пустой каталог | В какой режим смотрит env.js, есть ли товары в соответствующей базе, опубликованы ли они |
| В браузере CORS | Совпадают ли схема/домен/порт с CORS_ORIGINS; не используется ли неверный API_URL |
| Фото пропали после обновления | Используется ли постоянный volume/disk; что в PUBLIC_API_URL и ссылках /media |
| Письмо не пришло | SMTP-настройки, исходящее соединение, папка спама, проверка реальным письмом |
| Старая версия оформления | Правильная .public, версия подключений, кеш браузера; сборку повторить после исходных правок |
| HTTP 429 | Лимиты API/Nginx, Retry-After и очередь действий |
| Сборщик отказал | Безопасность пути и маркер владения; не подменять маркер без выяснения |

Для журналов замените многоточие полной командой:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs --tail=100 backend web
```

Журналы могут содержать контакты и детали ошибок. Перед передачей третьим лицам их нужно просмотреть. Не печатайте обычный `docker compose config` в публичный отчёт: он может раскрыть подставленные секреты.

## Копии и восстановление

Backup делает первую попытку сразу, затем примерно раз в 24 часа. Сохраняет пару `kbch-ДАТА.dump` и `media-ДАТА.tgz`; при сбое удаляет временные файлы и сохраняет старые копии. Копии базы и файлов снимаются последовательно, поэтому это не единый атомарный снимок всех данных. Для согласованного восстановления учитывайте момент загрузки фотографий.

Срок хранения — BACKUP_KEEP_DAYS, копии лежат на том же сервере и требуют внешнего копирования. Отдельного облачного backup или контроля успешности внешней копии в Compose нет. Проверяйте журналы backup и периодически пробуйте восстановление в изолированной среде.

Полное восстановление базы и media и откат — [14](14-Запуск-за-час.md). Откат только кода не откатывает схему базы и данные. `docker compose down -v` удаляет named volumes, включая базу, фото и сертификаты. Не использовать его как обычную команду обновления.

## Render и GitHub Pages

render.yaml описывает три ресурса: PostgreSQL, API с постоянным диском и статическую витрину. Он не запускает Compose backup/certbot/Nginx: их функции зависят от отдельной настройки хостинга. Планы в YAML — параметры репозитория, актуальную доступность и стоимость проверяют в панели перед заказом.

Pages публикует только `demo/.public/` через composite action. Настройки аккаунтов, заказы и оплата демо локальны; настоящий Python API и PostgreSQL на Pages не запускаются. Удаление demo-расширения описано в [15](15-Демо-версия.md).

# 24. API, запросы и форматы данных

**API** — адреса, по которым браузер получает и изменяет данные магазина. Базовый путь — `/api`. Протокол HTTP переносит запросы, JSON — данные. Реализация: `backend/app/api/routers/`; входные правила: `backend/app/schemas/`; ответы: `backend/app/api/serializers.py`.

Локальная интерактивная схема — `http://localhost:8000/api/docs`, машинная — `/api/openapi.json`. В production они по умолчанию выключены. Webhook Kaspi намеренно исключён из OpenAPI и описан ниже.

## Из чего состоит запрос

```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json

{"email":"buyer@example.com","password":"пароль локального аккаунта"}
```

`GET` читает, `POST` создаёт или выполняет действие, `PUT` сохраняет представленное состояние, `PATCH` меняет отдельные поля, `DELETE` удаляет. После входа защищённые запросы используют заголовок `Authorization: Bearer <token>`. Токен непрозрачный случайный, это не JWT; сервер хранит его SHA-256-отпечаток и срок в таблице sessions. В браузере исходный токен находится в localStorage.

Текстовые параметры в адресе передаются после `?`, например `/api/products?all=1`. Значения необходимо кодировать через URLSearchParams/encodeURIComponent. При отправке JSON нужен Content-Type. В клиенте всё это выполняет `request()` из `frontend/js/store/remote.js`.

## Полная карта маршрутов

«Пользователь» означает действующую серверную сессию с проверками в `api/deps.py`, «админ» — дополнительную роль admin. Все пути ниже включают `/api`.

### Аккаунт: `/api/auth`

| Метод и путь | Входные поля | Результат / доступ |
|---|---|---|
| `POST /api/auth/register` | name, email, password | Создаёт неподтверждённого пользователя, отправляет код; публично |
| `POST /api/auth/verify` | email, code | Подтверждение почты и токен с пользователем |
| `POST /api/auth/resend` | email | Повторное письмо подтверждения |
| `POST /api/auth/login` | email, password | Токен и пользователь после проверки |
| `POST /api/auth/logout` | — | Завершить текущую сессию |
| `POST /api/auth/logout/all` | — | Завершить сессии пользователя |
| `GET /api/auth/me` | — | Текущий пользователь |
| `PATCH /api/auth/me` | name?, phone? | Изменить свой профиль |
| `DELETE /api/auth/me` | password | Удалить свой аккаунт с проверками обработчика |
| `POST /api/auth/password/change` | old, new | Сменить пароль пользователя |
| `POST /api/auth/password/forgot` | email | Запрос кода сброса |
| `POST /api/auth/password/reset` | email, code, password | Сброс и вход |

Код — шесть цифр. Имя регистрации — 2–80 символов. Email проверяется как EmailStr. Пароль имеет отдельную проверку `core/security.py`, поэтому `min_length=1` в Pydantic-схеме не означает разрешение однобуквенного пароля. Вход по коду без пароля и Google OAuth в актуальных маршрутах отсутствуют.

### Каталог и загрузки

| Метод и путь | Данные / параметры | Доступ |
|---|---|---|
| `GET /api/categories` | — | Все |
| `PUT /api/categories` | Полный массив категорий с subs | Админ; удаление занятой категории отклоняется |
| `GET /api/products` | `all=1` для скрытых | Все; скрытые — только админ с параметром |
| `GET /api/products/{key}` | ID или slug | Все; скрытый товар виден админу |
| `POST /api/products` | ProductIn | Админ; HTTP 201 |
| `PUT /api/products/{product_id}` | ProductIn | Админ; передавать полное состояние редактируемого товара |
| `DELETE /api/products/{product_id}` | — | Админ |
| `POST /api/uploads` | data: data URL base64, folder: products/site | Админ; HTTP 201, ответ `{ "url": "…" }` |

ProductIn: name 1–160, brand ≤80, price 0–100000000, stock 0–1000000, до 20 images с адресами ≤500 символов. `status` — published/hidden. Дополнительные поля товара разрешены и проходят очистку/ограничение JSON; основные поля хранятся отдельными колонками. `oldPrice` передаётся в camelCase, колонка — old_price. Slug нормализуется и при совпадении получает суффикс. Категория, если задана, должна существовать.

Загрузка — JSON с data URL, а не multipart/form-data. Принимаются JPG/PNG/WEBP, проверяются base64, размер и сигнатура. Сервер назначает случайное имя файла. Эта проверка не является полным декодированием и анализом изображения. Загруженный файл и запись товара сохраняются отдельными действиями.

### Заказы и оплата

| Метод и путь | Что делает | Доступ |
|---|---|---|
| `GET /api/payments/methods` | Список включённых настроенных методов | Все |
| `POST /api/orders` | Создаёт заказ из OrderIn; HTTP 201 | Пользователь |
| `GET /api/orders/my` | Собственные заказы | Пользователь |
| `GET /api/admin/orders` | Все заказы | Админ |
| `PATCH /api/admin/orders/{order_id}` | status и/или paymentStatus | Админ |
| `DELETE /api/admin/orders/{order_id}` | Удаляет запись заказа | Админ |
| `POST /api/payments/sandbox/{order_id}` | Тестовая оплата/отмена | Владелец заказа |
| `POST /api/payments/kaspi/webhook` | Уведомление по реализованному контракту | HMAC-подпись, включённый kaspi_pay |

Пример OrderIn, где `p-example` нужно заменить ID существующего доступного товара:

```json
{
  "name": "Тестовый покупатель",
  "phone": "+7 (701) 123-45-67",
  "email": "buyer@example.com",
  "delivery": "pickup",
  "city": "",
  "address": "",
  "comment": "Учебный заказ в локальном режиме",
  "payment": "cash",
  "items": [{"id": "p-example", "qty": 1}]
}
```

Клиент передаёт ID и количество, контакты и выбранные способы. Цену, итог, пользователя и статус назначает сервер. В заказе до 50 строк, qty 1–99. Для courier/kazakhstan нужны город и адрес. Для pickup они необязательны.

Сервер пропускает скрытые, отсутствующие и закончившиеся товары; количество уменьшает до доступного остатка. Если ничего не осталось — HTTP 409. Поэтому успешный заказ может отличаться от исходной корзины. Остатки блокируются на PostgreSQL и изменяются в транзакции. SQLite не воспроизводит все гарантии конкурентности PostgreSQL.

Ответ включает id, number, userId, status, контакты, delivery, payment, paymentTitle, paymentStatus, paid, items, subtotal, deliveryPrice, total, createdAt и при наличии paymentInstructions. Суммы — целые тенге. Номер для покупателя начинается с 1001, внутренний ID имеет вид `o-…`.

| Поле | Допустимые значения |
|---|---|
| delivery | courier, kazakhstan, pickup |
| status | new, processing, shipped, done, cancelled |
| paymentStatus | pending, awaiting, paid, failed, refunded |

Отмена статуса заказа возвращает остатки; восстановление из cancelled снова проверяет и списывает их. Удаление записи заказа не вызывает этот механизм возврата. Статус refunded — учётная отметка, автоматического возврата денег через банк в коде нет. Общего idempotency key для POST /orders нет: при сетевой неопределённости сначала проверить список заказов, чтобы не создавать повтор.

SandboxPayIn: `action` pay/cancel, `card`, `expiry` в MM/YY, `cvc`. Использовать только тестовые данные из [10](10-Оплата.md). Этот интерфейс не является настоящим эквайрингом.

Реализованный webhook читает заголовок `X-Signature`: hex HMAC-SHA256 исходного тела с KASPI_WEBHOOK_SECRET. Поля JSON — orderId, status, amount. paid/success/completed считаются успехом; amount должен быть целым неотрицательным числом либо строкой цифр и совпадать с total. Повторы для уже paid/refunded возвращают ok. Такой контракт необходимо отдельно подтвердить с провайдером; наличие кода не подтверждает боевую интеграцию.

### Отзывы

| Метод и путь | Поля / параметры | Доступ |
|---|---|---|
| `GET /api/reviews` | productId?, all?, voter? | Публичные отзывы; свои скрытые доступны автору, all — админу |
| `POST /api/products/{product_id}/reviews` | rating, text, title?, pros?, cons?, recommend?, period? | Пользователь; создаёт или обновляет свой отзыв |
| `POST /api/reviews/{review_id}/vote` | voter | Пользователь либо гость с идентификатором voter |
| `PATCH /api/reviews/{review_id}/status` | status: published/hidden | Админ |
| `POST /api/reviews/{review_id}/reply` | text, пустая строка убирает ответ | Админ |
| `DELETE /api/reviews/{review_id}` | — | Автор или админ |

rating — 1–5, text — 20–1500, title ≤80, pros/cons ≤200, period — пусто/lt1/1to3/gt3. Имя берётся из аккаунта, а не из присланного поля. Ответ сохранения — `{updated, review}`. Поле verified означает наличие товара в неотменённом заказе пользователя; получение и оплата для этой отметки отдельно не проверяются. Гостевой voter хранится в браузере, поэтому он не доказывает уникальность физического человека.

### Сайт, пользователи и служебные запросы

| Метод и путь | Что делает | Доступ |
|---|---|---|
| `GET /api/site` | Замены фото sitePhotos | Все |
| `PUT /api/site/photos` | index 0–5, url; пустой url убирает замену | Админ |
| `GET /api/admin/users` | Список пользователей | Админ |
| `PATCH /api/admin/users/{user_id}` | blocked?, name? | Админ |
| `DELETE /api/admin/users/{user_id}` | Удаляет пользователя с проверками | Админ |
| `GET /api/bootstrap` | Начальные данные; voter? | Состав зависит от сессии |
| `GET /api/admin/system` | Режим, готовность почты/оплаты, проблемы настроек | Админ |
| `GET /api/health` | `SELECT 1` в базе, `{ "status": "ok" }` | Все; HTTP 503 при ошибке базы |

Bootstrap отдаёт user, categories, products, reviews, orders, users, site, payments, config. Гостю orders/users пусты, покупателю — свои, админу — полный набор. config содержит freeShippingFrom и courierPrice. Чувствительные поля пароля/токена/почтовых кодов сериализатор пользователя не отдаёт.

## Ошибки

| HTTP | Типичная причина |
|---|---|
| 400 | Действие недопустимо, неверный формат уведомления |
| 401 | Нужен вход или сессия недействительна |
| 402 | Тестовая оплата отклонена |
| 403 | Не хватает прав либо неверная подпись |
| 404 | Объект отсутствует или скрыт для текущего пользователя |
| 409 | Конфликт остатков, статуса, занятой категории, суммы |
| 413 | Тело запроса или фото слишком большое |
| 422 | Ошибка полей, формата или бизнес-проверки |
| 429 | Лимит попыток, может присутствовать Retry-After |
| 500 | Необработанная серверная ошибка |
| 502 / 503 | Внешний платёжный сервис / база недоступны |

Обычно JSON ошибки имеет `detail` со строкой. Pydantic может вернуть список ошибок полей, отдельные обработчики — объект с message/code. Клиент учитывает эти варианты. Часть ошибок может прийти от Nginx до API и иметь другой формат. Успешный health не проверяет SMTP, платёжный сервис, резервные копии и все бизнес-сценарии.

## Границы текущего API

Списки bootstrap/products и ряд других запросов не имеют серверной пагинации: фильтры и страницы каталога обрабатываются в браузере. Корзина и избранное не синхронизируются между устройствами. Постоянного WebSocket-канала нет; для обновления используется refresh/повторная загрузка. При большом каталоге эти решения требуют отдельного развития.

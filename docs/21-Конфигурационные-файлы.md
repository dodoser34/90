# 21. Конфигурационные файлы: редактор, Git, тесты, CI и хостинг

**Конфигурация** описывает, как инструмент должен работать. Она обычно не содержит бизнес-логику магазина. Здесь перечислены служебные файлы, включая скрытые имена с точкой. Переменные сервера подробно описаны в [23](23-Переменные-окружения.md).

## `.editorconfig` — правила редактора

Имя файла именно `.editorconfig`, а не «edit config». Его читает редактор с поддержкой EditorConfig.

| Правило | Значение | Эффект |
|---|---|---|
| `root` | `true` | Выше этой папки другой EditorConfig не ищется |
| `[*]` | Все файлы | Общая область применения |
| `charset` | `utf-8` | Русские тексты сохраняются в UTF-8 |
| `end_of_line` | `lf` | Перевод строки LF, в том числе на Windows |
| `indent_style` | `space` | Пробелы вместо табуляции |
| `indent_size` | `2` | Базовый размер отступа 2 пробела |
| `insert_final_newline` | `true` | Перевод строки в конце файла |
| `trim_trailing_whitespace` | `true` | Удалять пробелы в конце строки |
| `[*.md]` | `trim_trailing_whitespace=false` | Сохранять конечные пробелы Markdown, где они могут означать перенос |

Отдельной секции для Python нет, хотя Python-исходники используют 4 пробела. При правке `.py` сохраняйте отступы окружающего кода. EditorConfig не переформатирует весь проект сам и не является проверкой синтаксиса.

## `.prettierrc.json` — форматирование

| Поле | Значение | Смысл |
|---|---|---|
| `printWidth` | `140` | Предпочтительная ширина строки, а не абсолютный запрет длинных строк |
| `singleQuote` | `true` | Предпочитать одинарные кавычки в поддерживаемых форматах |
| `trailingComma` | `"none"` | Без завершающей запятой в списках, где это применимо |
| `endOfLine` | `"lf"` | Использовать LF |

Файл задаёт параметры Prettier, но команда форматирования и версия Prettier не закреплены. Prettier обычно используется через редактор. Поддержка Python этим файлом не настроена. Массовое форматирование не требуется для запуска магазина.

## `.gitattributes` — представление файлов в Git

`* text=auto eol=lf` включает распознавание текста и LF при выдаче файлов. PNG, JPG, JPEG, WEBP явно помечены как бинарные: Git не должен менять в них переводы строк. Это особенно важно для `entrypoint.sh`: Linux должен прочитать shell-файл корректно. `.gitattributes` не исключает файлы из Git и не шифрует их.

## `.gitignore` — что не добавлять в историю

| Файл | Дополнительные правила |
|---|---|
| Корневой `.gitignore` | Секреты, базы, письма, окружения, кеши, сборки, локальные редакторы/AI-настройки, личные выгрузки |
| `backend/.gitignore` | Загруженные `media/`, `uploads/`, данные и журнал писем |
| `frontend/.gitignore` | Локальные материалы, экспорт, галерея для проверки декора |
| `deploy/.gitignore` | Реальный `.env`, сертификаты, копии и локальные данные сервисов |
| `demo/.gitignore` | Публичная демо-сборка и её служебные файлы, кеши |

Шаблоны `.env.example`, `.env.sample`, `.env.template` разрешены исключениями `!…`. Они описывают имена переменных, а не должны содержать реальные пароли.

```powershell
git status --short
git check-ignore -v deploy/.env backend/dev.db
```

Игнорирование не удаляет файл, который уже отслеживается Git, и не стирает секрет из истории. Отдельные правила `.dockerignore` и публичного сборщика отвечают за другие каналы копирования.

## `backend/.dockerignore` — состав Docker-образа

Контекст сборки backend — папка `backend/`. `.dockerignore` исключает из него секреты, локальные базы, media, окружения, кеши, тесты, dev-зависимости и README. Поэтому `COPY . .` не должен переносить эти материалы в образ. Наличие `.gitignore` само по себе не влияет на Docker.

## Файлы тестов и миграций

| Файл | Значение |
|---|---|
| `pytest.ini` в корне | `testpaths=tests/general`: обычный запуск pytest из корня проверяет публичную сборку |
| `backend/pytest.ini` | `testpaths=tests`, `asyncio_mode=auto`, область асинхронного цикла — отдельная функция |
| `backend/alembic.ini` | Папка `migrations`, шаблон имён с датой и revision, настройки журналов; URL базы здесь пуст |
| `backend/migrations/env.py` | Берёт URL из Settings, подключает metadata моделей, выполняет online/offline миграции; для SQLite использует batch-режим |
| `backend/migrations/script.py.mako` | Шаблон новой миграции, создаваемой Alembic |

Pytest выбирает конфигурацию с учётом точки запуска и переданных путей. Команды для разных наборов указаны явно в [16](16-Тесты-и-проверка-качества.md). `alembic downgrade base` из CI предназначен для одноразовой тестовой базы и удаляет её схему.

## Настройки сайта и демо

| Файл | Кто читает | Назначение |
|---|---|---|
| `frontend/env.js` | `js/app.js` | Публичный адрес API; пустая строка включает локальный режим |
| `deploy/env.js` | Браузер через Nginx | Вариант с `KBCH_API_URL='/api'` для одного домена |
| `frontend/js/config.js` | Браузер | Название, контакты, локальные цены доставки, локальный список администраторов |
| `frontend/texts/ru/*.js` | Загрузчик и `core/texts.js` | Надписи, метаданные, подписи полей |
| `frontend/.nojekyll` | GitHub Pages | Не применять обработку Jekyll к опубликованной статике |
| `demo/config.json` | `demo/build.py` | Префикс памяти `kbch.demo.v1.`, список данных, runtime, страниц и CSS расширения |

Адрес API и `config.js` видны посетителю. Секреты сюда не помещают. `adminEmails` влияет только на локальный режим; сервер проверяет роль по своей базе и Settings.

## Настройки публикации

| Файл | Что задаёт |
|---|---|
| `backend/Dockerfile` | Python-образ, установку requirements, пользователя `app`, рабочую папку, entrypoint и порт 8000 |
| `backend/entrypoint.sh` | Проверку настроек, прав media, миграции и Gunicorn; при переданных аргументах выполняет их вместо обычного запуска |
| `deploy/.env.example` | Образец настроек оператора; реальный файл — `deploy/.env` |
| `deploy/docker-compose.yml` | Сервисы, сети, тома, healthchecks, перезапуск, журналы, подстановки переменных |
| `deploy/nginx/default.conf.template` | HTTP→HTTPS, домены, `/api/`, `/media/`, статику, правила кеша и запреты |
| `deploy/nginx/security.conf` | Общие лимиты запросов/соединений и сетевые таймауты |
| `deploy/nginx/headers.conf` | CSP, HSTS и другие защитные заголовки |
| `render.yaml` | Blueprint базы, Docker API с диском и статического сайта; сборка использует `API_URL` |

В Compose `${NAME}` подставляется из окружения/`.env`; `${NAME:-value}` даёт значение по умолчанию; `${NAME:?сообщение}` требует заполнения. `$$` оставляет знак `$` для shell внутри контейнера. Поля `env_file` и `environment` передают настройки контейнеру, причём явно заданное `environment` перекрывает `env_file`.

## GitHub Actions: автоматические действия

| Workflow | Когда запускается по текущему YAML | Что выполняет |
|---|---|---|
| `backend.yml` | Push с изменениями backend/workflow; PR с изменениями backend | Python 3.11, зависимости, матрица SQLite/PostgreSQL; для PostgreSQL upgrade/check/downgrade; тесты; ожидание отказа production без настроек |
| `checks.yml` | Push/PR по указанным путям frontend, tests, demo и сборщика; набор путей для push и PR немного различается | Node 20: `node --check`, JS-тесты; Python: тесты сборки, опциональные demo-тесты, сборка `.public/` |
| `pages.yml` | Push в `main` по frontend/demo/сборщику/workflow, либо ручной запуск | Проверяет наличие demo action и вызывает публикацию |
| `demo/github-pages/action.yml` | Вызывается из `pages.yml` | Настройка Pages, сборка демо, проверка фото, загрузка артефакта и deploy |

`permissions` ограничивают права job, `concurrency` отменяет устаревшую публикацию Pages. Секреты production в эти файлы не вписываются. Изменение только документации не обязательно запускает workflows из-за `paths`. Зелёный workflow подтверждает именно выполненные им шаги, а не каждую возможную проверку проекта.

## Создаваемые файлы

`.public-build.json` в корне и аналогичный файл в `demo/` — служебные маркеры владения результатом сборки. Сборщик проверяет их перед заменой непустой `.public/`, чтобы не затереть постороннюю папку. Это не настройки магазина. Кеши `.pytest_cache`, `__pycache__`, окружение `.venv`, базы и `.public/` создаются при работе и не редактируются как исходники.

Локальные папки `.claude/`, `.codex/`, `.agents/`, `.vscode/`, `.idea/` могут присутствовать у разработчика, но игнорируются Git. Они не являются обязательной частью запуска или публикации магазина.

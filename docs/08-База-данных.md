# 8. База данных: где лежат записи магазина

## Главное для владельца

База данных хранит товары, покупателей, заказы и отзывы. **SQLite** — база в одном файле `backend/dev.db` для локальной проверки. **PostgreSQL** — отдельная программа хранения данных для рабочего сервера.

Тексты инструкций, исходный код и картинки из `frontend/assets/images/` не являются базой. Загруженные через админ-панель фото тоже хранятся отдельно от неё. Поэтому полноценная резервная копия магазина должна содержать и базу, и загруженные фотографии.

Для повседневной работы используйте админ-панель. Ручное изменение таблиц нужно разработчику или администратору сервера, когда обычной формы недостаточно.

## Что хранится в таблицах

**Таблица** — набор однотипных записей. Например, одна строка в таблице товаров описывает один товар. **Поле** — отдельное значение строки: цена, название или остаток.

| Таблица | Содержимое |
|---|---|
| `users` | Имя, почта, телефон, отпечаток пароля, роль, подтверждение почты, блокировка |
| `sessions` | Действующие входы пользователей и сроки их действия |
| `email_codes` | Отпечатки кодов подтверждения и сброса пароля, срок и число попыток |
| `categories` | Категории, порядок, значки и подкатегории |
| `products` | Товары: адрес, цена, остаток, статус и дополнительные данные |
| `reviews` | Отзывы, оценки, ответ магазина и отметка подтверждённой покупки |
| `review_votes` | Голоса «Полезно» |
| `orders` | Номер, контакты, доставка, товары, суммы, способ и статусы оплаты и заказа |
| `site_settings` | Настройки сайта, в том числе фото страницы «О нас» |

Описание таблиц находится в `backend/app/db/models.py`, подключение — в `backend/app/db/session.py`.

У товара цена, остаток и статус вынесены в отдельные поля. Описание, состав, применение, фотографии и дополнительные разделы собраны в поле `data` формата **JSON** — вложенный набор именованных значений. Это позволяет добавлять разделы описания без новой колонки для каждого из них.

В заказ записывается собственный список товаров с ценой и количеством на момент оформления. Позднее изменение цены товара не переписывает уже сохранённый состав заказа.

## Входы, коды и удаление

**Сессия** — сохранённый вход пользователя. По умолчанию она действует 30 дней. В базе хранится отпечаток токена входа, а не сама строка токена.

Код из письма по умолчанию живёт 10 минут. Разрешены пять попыток проверки; новый код можно запросить не раньше чем через минуту. Настройки можно изменить, поэтому эти числа относятся к значениям по умолчанию.

В модели PostgreSQL связи при удалении настроены так:

- При удалении пользователя удаляются его сессии. Заказы и отзывы сохраняются без связи с аккаунтом.
- При удалении товара удаляются его отзывы и голоса к ним.
- При удалении отзыва удаляются его голоса «Полезно».

Удаление аккаунта не стирает автоматически контакты и состав старых заказов. Они сохранены как отдельная история заказов. Ограничение повторного голоса относится к сочетанию отзыва и идентификатора голосующего; оно не доказывает уникальность человека.

## Как база помогает избегать ошибок

В таблицах есть **ограничения** — правила, которые база проверяет при сохранении. Например: цена и остаток неотрицательные, оценка отзыва от 1 до 5, статусы только из разрешённого списка, почта пользователя и адрес товара уникальны.

Есть **индексы** — дополнительные указатели для ускорения поиска по часто используемым полям. Это похоже на указатель в конце книги: он помогает быстрее найти нужную запись.

Запросы в текущем коде строятся через SQLAlchemy с параметрами: значение пользователя передаётся отдельно от текста команды базы. Новые запросы должны сохранять это правило.

Для PostgreSQL число одновременных подключений ограничено, а слишком долгий запрос по умолчанию прерывается через 15 секунд. Для облачного подключения можно включить шифрование `DB_SSL=true`. В схеме Docker Compose база находится во внутренней сети и не публикует порт в интернет.

Эти свойства описывают текущую реализацию. Они не отменяют необходимость проверять новые запросы и права доступа.

## Технические подробности: изменение структуры

**Миграция** — файл с изменением структуры базы: создать таблицу, добавить поле или ограничение. История находится в `backend/migrations/versions/`.

| Часть имени файла | Назначение |
|---|---|
| `20261014_…_initial.py` | Создание таблиц |
| `20261014_…_constraints.py` | Дополнительные ограничения и индексы |
| `20261015_…_remove_google_and_code_login.py` | Удаление остатков прежних способов входа |

При обычном запуске контейнера `backend/entrypoint.sh` выполняет `alembic upgrade head` — применяет ещё не выполненные миграции. До обновления рабочего сервера нужно прочитать конкретные изменения и сохранить резервную копию.

Для локальной разработки команды выполняются в PowerShell **из папки `backend`**. Проверка соответствия моделей истории миграций:

```powershell
.\.venv\Scripts\python.exe -m alembic check
```

После изменения `app/db/models.py` разработчик создаёт файл миграции:

```powershell
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "describe change"
```

`describe change` нужно заменить коротким описанием изменения. Автоматически созданный файл обязательно просматривают. Затем на подготовленной базе применяют:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

Локальная база, созданная автоматически при первом запуске, может уже содержать таблицы без отметки миграций. Ошибку «таблица уже существует» нельзя исправлять повторным запуском вслепую: сначала проверьте состояние базы и историю Alembic. Не удаляйте базу с нужными данными.

Команда `alembic downgrade -1` откатывает последнюю миграцию. Она может удалить поля и данные, поэтому не является универсальной кнопкой отмены.

## Резервные копии

При работе через Docker Compose отдельный контейнер `backup` делает первую копию после запуска, затем повторяет примерно каждые 24 часа. В `deploy/backups/` сохраняются файл базы `kbch-…dump` и архив фотографий `media-…tgz`.

По умолчанию копии старше 14 дней удаляются. Срок задаёт `BACKUP_KEEP_DAYS`. Копии нужно забирать за пределы сервера: файлы на том же диске не спасут при потере сервера.

Как сделать ручную копию и восстановить данные, описано в [разделе 13](13-Публикация-на-сервере.md). Сам факт наличия файла копии не подтверждает, что восстановление пройдёт: его нужно отдельно проверять.

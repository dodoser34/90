# 16. Как проверить, что изменения работают

Тест — программа, которая сравнивает результат с ожидаемым. Например, проверяет, что заказ рассчитывается по цене сервера. Наличие тестов в папке не означает, что они прошли: результат относится к конкретному запуску и версии проекта.

Для правки текста руководства не нужно запускать серверные тесты. Для изменения программы выбирайте наборы, которые проверяют затронутое поведение. После изменения оформления обязательно посмотрите страницы в браузере.

## Что проверять

| Набор | Назначение |
|---|---|
| `tests/frontend/` | JavaScript: корзина, избранное, фильтры и вспомогательные функции |
| `tests/general/` | Публичная сборка: состав файлов, стили, пути и адрес API |
| `demo/tests/` | Сборка демо, отдельное хранение данных, фотографии и версии ресурсов |
| `backend/tests/` | API: аккаунты, права, каталог, база, заказы, отзывы, загрузки, тестовая оплата и настройки |

Внутри серверного набора есть отдельные файлы `test_security.py`, `test_validation_cases.py`, `test_catalog_cases.py`, `test_database_cases.py`, `test_order_scenarios.py`, `test_sandbox_payments.py`, `test_payment_contract.py` и `test_readiness.py`. Имена помогают выбрать нужную проверку. Проверка платёжного контракта использует подмену провайдера и не выполняет настоящий банковский платёж.

## Подготовить проверку на Windows

**Что открыть:** PowerShell в корне проекта. В этой папке видны `backend`, `frontend`, `tests` и `demo`.

Понадобятся Python 3.11 и Node.js 20 — версии, используемые автоматическими проверками проекта. Проверить наличие:

```powershell
python --version
node --version
```

Если виртуального окружения ещё нет, создайте его. Это отдельная папка с пакетами проекта:

```powershell
python -m venv backend/.venv
```

Установите закреплённые зависимости и проверьте их совместимость:

```powershell
& .\backend\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
& .\backend\.venv\Scripts\python.exe -m pip check
```

**Результат:** установка завершена, `pip check` сообщает `No broken requirements found`. Активировать окружение отдельной командой не нужно: команды ниже явно запускают Python из этой папки. На Linux и macOS аналогичный путь — `backend/.venv/bin/python`.

## Проверить сайт, сборку и демо

Из корня проекта в PowerShell:

```powershell
$testFiles = Get-ChildItem -LiteralPath tests/frontend -Filter *.test.cjs
node --test $testFiles.FullName
& .\backend\.venv\Scripts\python.exe -m pytest tests/general -q
& .\backend\.venv\Scripts\python.exe -m pytest demo/tests -q
```

**Результат:** каждый запуск завершается без ошибок; в отчёте нет `failed` или `error`. Число случаев может меняться при развитии проекта. Тесты сборки используют временные каталоги.

Чтобы отдельно найти ошибки синтаксиса во всех файлах JavaScript:

```powershell
Get-ChildItem frontend -Recurse -Filter *.js | ForEach-Object {
  node --check $_.FullName
  if ($LASTEXITCODE -ne 0) { throw "Ошибка синтаксиса: $($_.FullName)" }
}
```

Отсутствие ошибок здесь означает лишь, что код удалось разобрать. Это не проверка изображения страницы и всех действий пользователя.

## Проверить API в отдельной тестовой базе

**Важно:** серверные тесты удаляют и создают таблицы перед сценариями. В `TEST_DATABASE_URL` нельзя указывать рабочую базу или базу с нужными данными.

Для обычной локальной проверки оставьте эту переменную пустой: тогда тесты создадут временную SQLite. Выполните из корня проекта:

```powershell
$env:TEST_DATABASE_URL = ''
Set-Location backend
& .\.venv\Scripts\python.exe -m pytest -q
Set-Location ..
```

**Результат:** серверные проверки прошли, а PowerShell снова находится в корне проекта. После ошибки тестов также выполните `Set-Location ..`, прежде чем запускать команды для корня.

Для одного сценария из папки `backend`:

```powershell
& .\.venv\Scripts\python.exe -m pytest tests/test_order_scenarios.py -q
```

Для списка случаев без выполнения используйте `-m pytest --collect-only -q`. Зависимости всё равно нужны: подготовка тестов импортирует приложение.

SQLite удобна локально, но не воспроизводит все особенности одновременной работы PostgreSQL. Для проверки PostgreSQL выделяют отдельную одноразовую базу и задают её адрес через `TEST_DATABASE_URL`. При этом письма и платёжный провайдер в тестах подменяются. Настоящую SMTP-отправку и оплату проверяют отдельно.

## Проверить глазами в браузере

1. Запустите нужный режим по [главе 2](02-Как-запустить.md). Проверяйте API, если меняли сервер; для демонстрации интерфейса можно использовать демо.
2. Пройдите затронутый путь: например, каталог → товар → корзина → заказ → просмотр администратором.
3. На компьютере и телефоне проверьте читаемость, отсутствие лишней горизонтальной прокрутки, доступность кнопок и полей.
4. Проверьте клавиатуру, закрытие окон клавишей Esc и работу при отключённых анимациях.
5. В инструментах разработчика браузера проверьте Console — ошибки программы — и Network — неудачные загрузки. Не должно быть неожиданных ошибок 404 и 500.
6. После правки CSS сравните исходный локальный сайт и опубликованную сборку: сборка объединяет стили.

**Запишите:** дату, версию кода, браузер, размер окна, выполненные действия и итог. Полный список приёмки рабочего магазина — [глава 14](14-Запуск-за-час.md).

## Где смотреть автоматические результаты GitHub

Откройте репозиторий → Actions → нужный запуск. `backend.yml` проверяет SQLite и PostgreSQL, а также миграции — изменения структуры базы. `checks.yml` проверяет JavaScript и сборки. `pages.yml` публикует демо.

Запуски зависят от изменённых путей и события. Правка только документации не обязана запускать проверки. Полноценного браузерного E2E-workflow и отчёта покрытия в репозитории нет. Успешные автотесты не заменяют проверку рабочего домена, писем, фотографий и реального провайдера оплаты.

# 9. Безопасность: что защищено и что проверять

## Главное для владельца

Настоящую проверку входа, прав, цен и заказов выполняет сервер. Режим без сервера и демо подходят для показа; их данные находятся в браузере пользователя.

В рабочем магазине защиту обеспечивают настройки веб-сервера, проверки Python и правила базы. Этот раздел объясняет реализованные меры. Он не является результатом отдельного полного аудита и не обещает отсутствие ошибок.

Практические задачи владельца: хранить секреты отдельно от исходников, использовать собственные пароли, проверять почту и резервные копии, устанавливать обновления осознанно.

## Пароли и вход

В базе хранится **хеш пароля** — специальный проверочный отпечаток. При входе bcrypt сверяет введённый пароль с этим отпечатком. Открытого пароля в базе нет. Случайная добавка, называемая **солью**, делает отпечатки одинаковых паролей разными.

bcrypt намеренно замедляет перебор. Это усложняет подбор, но слабый пароль всё равно может быть угадан. Пользовательский пароль по умолчанию должен содержать не менее восьми символов; код также отклоняет распространённые и слишком простые пароли и некоторые варианты с именем почты.

После входа браузер получает случайный токен. В базе хранится его отпечаток SHA-256. Коды из писем хранятся в виде HMAC-отпечатков с секретом сервера; обычный срок кода — 10 минут, число попыток — пять.

Код: `backend/app/core/security.py`, `backend/app/api/routers/auth.py`.

## Администратор

При рабочем размещении администратор задаётся настройками сервера: `ADMIN_EMAIL` и `ADMIN_PASSWORD` либо `ADMIN_PASSWORD_HASH`. Для открытого пароля требуется не менее 12 символов и отсутствие простых сочетаний из проверки конфигурации.

При каждом запуске сервер приводит выбранный аккаунт администратора к настройкам. У других аккаунтов роль администратора снимается. Удалить или заблокировать этот аккаунт через обычный интерфейс нельзя.

Вместо открытого пароля можно записать его bcrypt-хеш. Команда `hash-password` и место её запуска описаны в [разделе 7](07-Бэкенд-Python.md). Полученное значение тоже нужно хранить как секрет.

## Проверки прав и данных

Сервер проверяет роль на адресах управления магазином. Просто открыть страницу админ-панели или поменять вид кнопок в браузере недостаточно для серверных прав.

Сумма заказа вычисляется по ценам базы. При оформлении в PostgreSQL строки товаров блокируются на время изменения остатка, чтобы конкурирующие заказы не списали один и тот же остаток независимо друг от друга.

Тестовая оплата разрешена только владельцу заказа. Оплаченный, возвращённый или отменённый заказ повторно через тестовую форму не оплачивается. Настоящий перевод на Kaspi подтверждает администратор после проверки поступления денег.

Поля запросов проверяются на формат и длину. Текст очищается и экранируется: специальные символы выводятся как текст, чтобы введённая надпись не стала HTML-кодом. Такой подход снижает риск **XSS** — выполнения чужого скрипта на странице.

SQLAlchemy передаёт значения отдельно от команд базы. Это защищает реализованные запросы от **SQL-инъекции** — попытки превратить введённое значение в команду к базе. Новые запросы и новые места вывода текста должны сохранять эти правила.

Основные места: `backend/app/api/deps.py`, `backend/app/schemas/`, `backend/app/core/sanitize.py`, `frontend/js/core/utils.js`, `backend/app/api/routers/orders.py`.

## Загруженные фотографии

Сервер проверяет допустимый размер и начало содержимого JPG, PNG или WEBP, затем сам придумывает имя файла. Это мешает принять произвольный файл только по расширению `.jpg`.

По умолчанию максимальный размер изображения — 8 МБ. Проверка сигнатуры не равна полной проверке содержимого и не является антивирусом. Код: `backend/app/api/routers/catalog.py`.

## Ограничения частоты действий

Слишком частые обращения получают ответ **429** — «Слишком много попыток» с временем ожидания. IP — сетевой адрес, по которому сервер различает подключения; у нескольких людей он может быть общим.

| Действие | Значение по умолчанию | Настройка |
|---|---|---|
| Вход с одного IP | 10 в минуту | `RATE_LOGIN` |
| Вход в один аккаунт | 5 в минуту | `RATE_LOGIN_EMAIL` |
| Письма с кодами | 5 в минуту; повтор на почту не раньше минуты | `RATE_CODES`, `CODE_RESEND_SECONDS` |
| Регистрация с одного IP | 5 в час | `RATE_REGISTER` |
| Запись заказов, отзывов, голосов, загрузок | 60 в минуту для соответствующих действий | `RATE_WRITE` |
| Обращения к API с одного IP | 300 в минуту, кроме проверки здоровья | `RATE_GLOBAL` |

У Nginx есть отдельные ограничения: для сайта 30 запросов в секунду, для API 10 в секунду, для адресов входа 10 в минуту. Точные области применения и дополнительные параметры находятся в `deploy/nginx/`.

Лимиты Python хранятся в памяти каждого рабочего процесса, не объединяются между ними и сбрасываются при перезапуске. Они помогают против частого повторения запросов, но не защищают от любой распределённой атаки или перегрузки внешнего канала.

## Защита соединения и браузера

При публикации через Nginx используется **HTTPS** — шифрование между браузером и сайтом. Специальные заголовки ограничивают поведение браузера:

- `Content-Security-Policy`, или CSP: откуда разрешено загружать скрипты, стили, картинки и другие ресурсы.
- `Strict-Transport-Security`: просьба к браузеру использовать HTTPS для следующих обращений.
- `X-Frame-Options: DENY` и `frame-ancestors 'none'`: запрет встраивания сайта в чужой фрейм.
- `X-Content-Type-Options: nosniff`: запрет угадывать тип ответа вместо указанного.
- `Permissions-Policy`: отключение доступа к камере, микрофону и геолокации для сайта.
- `Cache-Control: no-store`: ответы API с личными данными не должны сохраняться в кеше.

**CORS** задаёт, с каких адресов сайта браузер может читать ответы API. Это дополнительное браузерное правило; оно не заменяет серверную проверку токена и прав.

Токен хранится в localStorage и передаётся явно через `Authorization`, а не автоматически в cookie. Это снижает обычный риск CSRF — отправки действия от имени пользователя с чужого сайта. Однако JavaScript своего сайта имеет доступ к токену, поэтому предотвращение XSS остаётся обязательным.

В `frontend/404.html` встроенный скрипт разрешён по точному хешу. После его изменения нужно обновить хеш в HTML и в `deploy/nginx/headers.conf`, иначе браузер заблокирует скрипт.

## Секреты и публикация

`deploy/.env` содержит пароли и ключи. Его нельзя публиковать вместе с исходниками или отправлять как обычное приложение к инструкции. В рабочем запуске проверка конфигурации запрещает заведомо неподходящие настройки: слабый секрет, короткий открытый пароль администратора, SQLite вместо PostgreSQL, отсутствие нужной почты или неизвестный способ оплаты.

Для выдачи посетителям собирается папка `.public/`. Исходники Python, инструкции, `.env`, `.git` и резервные копии не должны раздаваться как содержимое сайта. Это обеспечивают сборка и настройки Nginx.

Если доверие к прокси включено, IP берётся из заголовка пересылки. Это безопасно только при правильной схеме, в которой запросы приходят через доверенный Nginx. Публиковать бэкенд в обход этой схемы без проверки настроек нельзя.

## Что проверить перед началом продаж

1. Проверка конфигурации не показывает ошибок рабочего режима.
2. У администратора собственный пароль, а секреты не используются в других проектах.
3. Письмо с кодом действительно приходит тестовому покупателю.
4. Сайт открывается по HTTPS, а HTTP переводит на HTTPS.
5. Создаются копии базы и фото; есть их экземпляр вне сервера.
6. На сервере настроен доступ по SSH-ключу и открыты только нужные сетевые порты согласно разделу 13.
7. В `PAYMENT_METHODS` оставлены только те способы, которые вы готовы показывать покупателям. Перед реальными продажами тестовые способы убраны.

Автоматические проверки описаны в [разделе 16](16-Тесты-и-проверка-качества.md). Они проверяют конкретные сценарии; прохождение тестов не заменяет проверку настроек и реального пути покупателя.

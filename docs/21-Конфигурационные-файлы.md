# 21. Конфигурационные файлы

Эта глава помогает понять служебные файлы проекта: что задаёт отступы, что исключает секреты из копирования, что запускает проверки и что управляет публикацией. Она нужна разработчику и человеку, который обслуживает сервер. Для изменения товаров читать её целиком не требуется.

**Конфигурация** — настройки работы программы. Имена с точкой в начале, например `.gitignore`, обозначают обычные файлы; проводник может скрывать их. Значения серверных настроек собраны отдельно в [главе 23](23-Переменные-окружения.md).

## Быстрый выбор файла

| Нужно понять или изменить | Где смотреть |
|---|---|
| Отступы и сохранение русских букв | `.editorconfig` |
| Оформление кода через Prettier | `.prettierrc.json` |
| Какие файлы не попадают в Git | `.gitignore` и вложенные `.gitignore` |
| Какие файлы не попадают в Docker-образ | `backend/.dockerignore` |
| Куда сайт отправляет запросы | `frontend/env.js` или `deploy/env.js` |
| Как запускаются сервисы на VPS | `deploy/docker-compose.yml` |
| Какие проверки выполняет GitHub | `.github/workflows/` |

## `.editorconfig`: отступы и кодировка

Редактор с поддержкой EditorConfig читает этот файл и применяет базовые правила.

| Правило | Значение | Что получится |
|---|---|---|
| `root` | `true` | Настройки EditorConfig из родительских папок не используются |
| `[*]` | Все файлы | Следующие общие правила относятся ко всем файлам |
| `charset` | `utf-8` | Кодировка для текста, включая русский |
| `end_of_line` | `lf` | Один вид перевода строки на Windows и Linux |
| `indent_style` | `space` | Отступы пробелами |
| `indent_size` | `2` | Основной отступ — 2 пробела |
| `insert_final_newline` | `true` | В конце файла есть перевод строки |
| `trim_trailing_whitespace` | `true` | Пробелы в конце строки удаляются |
| `[*.md]` | `trim_trailing_whitespace=false` | В Markdown конечные пробелы сохраняются: они могут означать перенос строки |

В Python-файлах проекта используются 4 пробела. Отдельного исключения для них в `.editorconfig` нет. При правке `.py` сохраняйте отступы окружающего кода: в Python они определяют структуру программы. EditorConfig не проверяет правильность кода и сам не переписывает все файлы.

## `.prettierrc.json`: предпочтения форматирования

Prettier — инструмент, который выравнивает код. Файл хранит только его настройки:

| Поле | Значение | Объяснение |
|---|---|---|
| `printWidth` | `140` | Предпочтительная ширина строки; более длинные строки всё же возможны |
| `singleQuote` | `true` | По возможности использовать одинарные кавычки |
| `trailingComma` | `"none"` | Не добавлять запятую после последнего элемента |
| `endOfLine` | `"lf"` | Использовать перевод строки LF |

Версия Prettier и команда его установки в проекте не закреплены. Обычно его подключают в редакторе. Этот файл не настраивает форматирование Python. Для запуска магазина массово форматировать код не нужно.

## `.gitattributes`: как Git хранит файлы

Правило `* text=auto eol=lf` помогает сохранять текст с переводами строк LF. PNG, JPG, JPEG и WEBP отмечены как двоичные файлы: Git не должен менять в них байты ради перевода строк. Правильный перевод строк особенно нужен `backend/entrypoint.sh`, который запускается в Linux.

Этот файл не скрывает секреты и не шифрует данные. За исключения из Git отвечает `.gitignore`.

## `.gitignore`: что не добавлять в историю

| Файл правил | Что исключает |
|---|---|
| Корневой `.gitignore` | Секреты, базы, письма, окружения, временные файлы, сборки, личные настройки редакторов и выгрузки |
| `backend/.gitignore` | Загруженные фото, локальные данные и журнал писем |
| `frontend/.gitignore` | Локальные материалы, экспорт и служебную галерею декора |
| `deploy/.gitignore` | Настоящий `.env`, сертификаты, резервные копии и локальные данные сервисов |
| `demo/.gitignore` | Результат демо-сборки и временные файлы |

Образцы `.env.example`, `.env.sample`, `.env.template` специально разрешены правилами с `!`. В них должны быть названия настроек и примеры, без настоящих паролей.

Из корня проекта можно выполнить:

```powershell
git status --short
git check-ignore -v deploy/.env backend/dev.db
```

Первая команда показывает изменения. Вторая показывает, какое правило исключает указанный файл. Если файл уже был добавлен в Git, добавление правила не уберёт его из истории. `.gitignore`, `.dockerignore` и публичный сборщик работают независимо: каждый отвечает за свой способ копирования.

## `backend/.dockerignore`: содержимое Docker-образа

При сборке Docker получает папку `backend/`. `.dockerignore` исключает из неё секреты, локальные базы, загруженные фото, окружения, временные файлы, тесты, зависимости для разработки и README. Поэтому команда `COPY . .` в Dockerfile не должна включать эти материалы в образ.

Правило в `.gitignore` само по себе не запрещает Docker копировать файл. Обновляйте нужный список исключений там, где реально используется копирование.

## Тесты и изменения базы

| Файл | Назначение |
|---|---|
| Корневой `pytest.ini` | При обычном запуске pytest из корня выбирает `tests/general`: проверки публичной сборки |
| `backend/pytest.ini` | Выбирает серверные тесты и включает автоматическую поддержку асинхронных тестов; цикл событий отдельный для каждой функции |
| `backend/alembic.ini` | Настройки Alembic: папка миграций, имена файлов и журналы; адрес базы здесь не заполнен |
| `backend/migrations/env.py` | Читает адрес базы из Settings, подключает описание таблиц и выполняет миграции; для SQLite использует специальный batch-режим изменения таблиц |
| `backend/migrations/script.py.mako` | Шаблон нового файла миграции |

**Миграция** — записанное изменение структуры базы. Например, добавление нового столбца. Адрес базы берётся из настроек приложения. Pytest выбирает конфигурацию по месту запуска и переданным путям, поэтому используйте точные команды из [главы 16](16-Тесты-и-проверка-качества.md).

В автоматических проверках встречается `alembic downgrade base`: она откатывает схему до начала истории. Там используется одноразовая тестовая база. Для рабочей базы такую команду не применяют как обычную проверку.

## Настройки витрины и демо

| Файл | Кто его читает | Что задаёт |
|---|---|---|
| `frontend/env.js` | Загрузчик `js/app.js` | Адрес API; пустая строка включает данные браузера |
| `deploy/env.js` | Браузер через Nginx | API `/api` для сайта и API на одном домене |
| `frontend/js/config.js` | Браузер | Название, контакты, местные цены доставки и список администраторов для локального режима |
| `frontend/texts/ru/*.js` | Загрузчик и `core/texts.js` | Надписи и описания страниц |
| `frontend/.nojekyll` | GitHub Pages | Отменяет дополнительную обработку сайта через Jekyll |
| `demo/config.json` | `demo/build.py` | Отдельный префикс памяти `kbch.demo.v1.` и список файлов демо-расширения |

Всё из `frontend/`, включая адрес API и `config.js`, может увидеть посетитель. Пароли и секретные ключи здесь не хранятся. `adminEmails` даёт права только в локальном режиме. На сервере роль проверяется по серверной базе и Settings.

## Файлы публикации

| Файл | Назначение |
|---|---|
| `backend/Dockerfile` | Собирает Python-образ, устанавливает библиотеки, создаёт пользователя `app`, задаёт запуск и порт 8000 |
| `backend/entrypoint.sh` | Проверяет настройки и папку фото, применяет миграции, запускает Gunicorn; если передана отдельная команда, выполняет её |
| `deploy/.env.example` | Образец настроек; рабочий файл называется `deploy/.env` |
| `deploy/docker-compose.yml` | Соединяет сервисы, сети, хранилища, проверки состояния и журналы |
| `deploy/nginx/default.conf.template` | Направляет запросы к сайту, API и фото, включает HTTPS и правила кеша |
| `deploy/nginx/security.conf` | Ограничивает частоту запросов и соединения, задаёт сетевые таймауты |
| `deploy/nginx/headers.conf` | Добавляет защитные HTTP-заголовки, включая CSP и HSTS |
| `render.yaml` | Описывает базу, API с постоянным диском и статический сайт для Render; сборка читает `API_URL` |

В Compose запись `${NAME}` подставляет значение настройки. `${NAME:-value}` использует `value`, если значение отсутствует. `${NAME:?сообщение}` требует заполнить настройку. `$$` оставляет один знак `$` для команды внутри контейнера. Через `env_file` передаётся файл настроек; значения из `environment` имеют над ним приоритет.

## GitHub Actions: автоматические проверки

**Workflow** — файл с последовательностью действий в GitHub. **Push** — отправка изменений. **Pull request**, сокращённо PR, — предложение внести их в основную ветку.

| Файл | Когда запускается | Что проверяет или публикует |
|---|---|---|
| `.github/workflows/backend.yml` | Push при изменениях backend или этого workflow; PR при изменениях backend | Python 3.11, SQLite и PostgreSQL, тесты; на PostgreSQL — применение, сверка и откат миграций; отказ production без настроек |
| `.github/workflows/checks.yml` | Push/PR при изменениях frontend, tests, demo и сборщика; точные списки немного отличаются | Node 20: синтаксис и JS-тесты; Python: общая сборка, существующие демо-тесты и создание `.public/` |
| `.github/workflows/pages.yml` | Push в `main` по указанным файлам frontend/demo/сборщика/workflow или вручную | Проверяет наличие действия демо и вызывает публикацию |
| `demo/github-pages/action.yml` | По вызову из `pages.yml` | Собирает демо, проверяет фото, передаёт результат в Pages и публикует |

`permissions` ограничивает права задания. `concurrency` отменяет устаревшую публикацию Pages. Секреты рабочего сервера не вписываются в эти YAML-файлы. Изменение только документации может не запускать проверки из-за фильтров `paths`. Зелёная отметка означает, что прошли именно перечисленные шаги.

## Файлы, которые создаются автоматически

`.public/` и `demo/.public/` — готовые файлы сайта. Рядом сборщики создают `.public-build.json`: отметку, что папка принадлежит этому сборщику. Перед заменой непустой папки отметка проверяется. Не создавайте её вручную ради обхода проверки.

`.venv`, `__pycache__`, `.pytest_cache`, локальная база и готовая сборка появляются во время работы. Исходники правят в соответствующих папках проекта. Личные папки редакторов, например `.vscode/` и `.idea/`, не нужны посетителю и не обязательны для запуска магазина.

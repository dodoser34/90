# 22. Карта папок и файлов

Эта глава нужна, когда вы знаете, что хотите изменить, но не знаете, в каком файле это находится. Это справочник, его не нужно читать подряд. Общее устройство магазина проще объяснено в [главе 3](03-Устройство-проекта.md).

Все пути отсчитываются от главной папки проекта. Например, `frontend/js/app.js` означает: открыть `frontend`, затем `js`, затем файл `app.js`. Косая черта в тексте обозначает переход в папку; на Windows в командах также встречается обратная черта.

## Сначала выберите задачу

| Что ищете | Куда перейти |
|---|---|
| Название, контакты и надписи | `frontend/js/config.js`, `frontend/texts/ru/`; инструкция — глава 12 |
| Цвета и оформление телефона | `frontend/css/`, особенно `base/variables.css` и `responsive/` |
| Корзину, избранное и действия страниц | `frontend/js/store/`, `frontend/js/pages/` |
| Серверные проверки и данные заказов | `backend/app/api/routers/orders.py`, `schemas/orders.py`, `db/models.py` |
| Настройки запуска | `backend/app/core/config.py`, `deploy/.env`; справочник — глава 23 |
| Публикацию и резервные копии | `deploy/`; инструкция — главы 13, 14 и 25 |

Дальше перечислены папки и основные файлы. «Исходники» — файлы, которые меняет разработчик. «Сборка» — подготовленная из них копия для публикации.

## `tests/` и `docs/`

`tests/frontend/helpers.cjs` создаёт упрощённое окружение вместо настоящего браузера внутри Node.js. `utils.test.cjs` проверяет помощники, `store.test.cjs` — хранилище, `catalog.test.cjs` — логику каталога. `tests/general/test_public_build.py` проверяет безопасный состав и работу публичной сборки. `tests/README.md` — краткие команды. Это отличается от `backend/tests/` и `demo/tests/`.

В `docs/` лежат главы 01–27, оглавление 00 и требования к фотографиям оформления. Это исходники документации Markdown, которые не входят в публичную витрину.

Для чтения без редактора подготовлены `docs/Руководство по магазину.docx` и `docs/Читать-в-браузере.html`. Первый файл открывается в приложениях для Word, второй — в обычном браузере. Их пересоздаёт `docs/tools/build_guide.py` после изменения исходных глав; порядок описан в главе 26.

## Какие папки содержат рабочие данные

| Папка или файл | Можно пересоздать? | Что учитывать |
|---|---|---|
| `.public/`, `demo/.public/` и маркеры сборщика | Да, из исходников | Ручные изменения исчезнут при сборке |
| `.venv/`, `__pycache__/`, `.pytest_cache/` | Да | Не являются данными магазина |
| `backend/dev.db` | Только с потерей локальных записей | Локальные аккаунты, каталог и заказы |
| `backend/dev-mail.log` | Новые письма создадут файл | Содержит коды локального режима |
| `backend/media/` или Docker volume `media` | Нет, нужны оригиналы/копии | Загруженные фотографии |
| Docker volume `pgdata` | Нет, нужна копия базы | Рабочие записи магазина |
| `deploy/backups/` | Это сами резервные данные | Хранить также вне сервера |
| `deploy/.env`, сертификаты | Нужны защищённая копия/перевыпуск | Не публиковать и не коммитить |

## Пример: от кнопки «Оформить» до базы

Для примера проследим оформление заказа:

1. `frontend/pages/checkout.html` содержит основу формы.
2. `frontend/js/pages/checkout.js` собирает введённые данные.
3. `frontend/js/store/remote.js` отправляет запрос API.
4. `backend/app/schemas/orders.py` задаёт допустимые поля и значения.
5. `backend/app/api/routers/orders.py` проверяет пользователя, товары и остатки.
6. `backend/app/services/payments/` подготавливает выбранную оплату, `backend/app/db/models.py` описывает сохранение заказа в базе.
7. `backend/app/api/serializers.py` превращает запись базы в ответ для браузера.

Если API выключен, заказ сохраняется только в браузере через `frontend/js/store/orders.js`. Наличие заказа в таком режиме не подтверждает, что его получил рабочий сервер.

Что важно понять до запуска

Демо — версия для знакомства с сайтом. Она содержит примеры товаров и хранит изменения в вашем браузере. Другой человек не увидит ваши заказы и изменения.

Магазин с сервером хранит товары, пользователей и заказы в общей базе. Именно такой режим нужен для работы с настоящими покупателями. Запуск сервера на своём компьютере ещё не делает сайт доступным в интернете.

Тестовая оплата только показывает, как проходит платёж. Она не списывает деньги. Настоящее подключение платёжного сервиса требует отдельной настройки и проверки.

Адрес localhost означает «этот компьютер». Если открыть такой адрес на телефоне, он будет указывать на сам телефон. Он не откроет магазин, запущенный на вашем ПК. Это ограничение запуска сайта; читать руководство на телефоне можно независимо от него.

Как понимать пути и команды

Корень проекта — главная папка, в которой лежат README.md и папки frontend, backend, deploy и docs. Если написано frontend/js/config.js, сначала откройте frontend, затем js, затем файл config.js.

Терминал — окно для ввода команд. В Windows можно открыть папку проекта в Проводнике, нажать адресную строку, ввести powershell и нажать Enter. Команды вводят в открывшемся окне. Для чтения документа терминал не нужен.

Строку из блока с командой копируйте целиком и нажимайте Enter. Если в блоке несколько строк, выполняйте их по очереди. Слова перед блоком объясняют, на каком компьютере и из какой папки запускать команду. Команды для Linux-сервера не нужно вводить в обычный PowerShell на своём ПК.

Команда cd backend означает «перейти в папку backend». Команда cd .. возвращает на одну папку выше. Сочетание Ctrl + C останавливает работающий сервер в том окне, где он запущен.

Если пример содержит example.kz или подпись «ваш домен», подставьте настоящий адрес своего сайта. Если написано «ваш пароль», задайте свой пароль. Не заменяйте имена параметров и команд произвольно.

1 Что это за проект

Главное за одну минуту

K-Beauty | C-Health — сайт магазина корейской косметики и натуральных трав для покупателей в Казахстане.

Покупатель находит товар, добавляет его в корзину и оформляет заказ. Владелец видит заказ в специальном разделе управления магазином — админ-панели. Там же он меняет товары, остатки, фотографии и статусы заказов.

Проект можно открыть на своём компьютере для знакомства. Для работы с настоящими покупателями его нужно отдельно разместить в интернете и настроить. Инструкции по этим двум задачам различаются.

Что может покупатель

  • Смотреть каталог, искать товары, выбирать категорию, бренд, назначение и цену.
  • Открывать карточку товара: фотографии, описание, состав, применение, характеристики и отзывы.
  • Сохранять избранное и собирать корзину без регистрации.
  • Зарегистрироваться, подтвердить почту кодом из письма и войти по почте и паролю.
  • Оформить заказ с доставкой или самовывозом.
  • Смотреть свои заказы, менять имя, телефон и пароль, писать и изменять свои отзывы.
  • Восстановить забытый пароль через письмо или удалить свой аккаунт.

Оформление заказа, личный кабинет и написание отзыва требуют входа. Для просмотра каталога вход не нужен.

Что может владелец

Администратор — человек с правами управления магазином. В админ-панели ему доступны товары, категории, заказы, пользователи, отзывы, фотографии страницы «О нас», обзор продаж и проверка настроек перед запуском.

Права администратора в магазине с сервером задаются настройками сервера. Обычная регистрация таких прав не даёт. Подробная инструкция — в разделе 11 «Админ-панель».

Что нужно знать об оплате

В проекте есть перевод на Kaspi с ручным подтверждением владельцем и оплата при получении. Отдельно есть тестовая оплата картой и через имитацию Kaspi. Она показывает ход оплаты, но денег не списывает.

Для Kaspi Pay в коде подготовлена отдельная заготовка подключения. Её работу с настоящим платёжным сервисом нужно проверить и при необходимости доработать. Само наличие этого кода ещё не означает, что магазин принимает настоящие онлайн-платежи. Подробнее — раздел 10 «Оплата».

Два режима для показа и для покупателей

Режим без сервера подходит для знакомства с сайтом. Данные сохраняются в браузере конкретного человека. Изменения на одном компьютере не появляются у другого посетителя. Очистка данных браузера может их удалить. В этом режиме нельзя полагаться на вход и роль администратора как на защиту настоящего магазина.

Режим с сервером нужен для общего каталога, аккаунтов и заказов. Сервер — постоянно работающая программа, к которой обращается сайт. Он проверяет права, считает сумму заказа и сохраняет данные в общей базе. Локально, то есть на своём компьютере, сервер можно запускать для проверки.

Адрес сервера задаётся в frontend/env.js. Пустой адрес включает режим без сервера. При публикации используются настройки выбранного способа размещения.

2 Как запустить на своём компьютере

Подготовка как вводить команды

Для запуска нужен Python 3.11 или новее. Python — программа, которая выполняет файлы проекта с расширением .py. VS Code для запуска не обязателен: команды можно вводить в обычном PowerShell.

На Windows откройте папку проекта в Проводнике. Это папка, внутри которой лежат frontend, backend, demo и deploy. Нажмите на строку адреса, напишите powershell и нажмите Enter. Откроется окно для команд — терминал.

Вставляйте только текст из блоков команд. После каждой команды нажимайте Enter и ждите результат. Не вводите адрес сайта в терминал: адрес нужно открывать в браузере.

Проверьте Python:

python --version

Ожидаемый результат — строка вида Python 3.11… или более новая версия. Если команда не найдена, установите Python и снова откройте PowerShell. Если на вашем компьютере работает команда py, вместо python в инструкциях можно использовать py.

Выберите один из трёх вариантов ниже. Для первого знакомства удобнее вариант 1. Файлы настроек .env для обычного локального запуска не нужны, если вы ещё не создавали собственные настройки.

Вариант 1 Посмотреть готовое демо

Демо — версия с примерами товаров, отзывов и заказов. Она подходит, чтобы понять работу магазина, не настраивая настоящую базу и почту.

В терминале, открытом в папке проекта, выполните:

python demo/serve.py

Когда появится строка Демо: http://localhost:5175, откройте в браузере http://localhost:5175. localhost означает «этот же компьютер».

На странице входа есть кнопки быстрого входа. Можно также ввести данные вручную:

Кому войтиПочтаПароль
Покупателюbuyer@demo.kzdemo123
Администраторуadmin@demo.kzadmin123

Эти данные относятся только к демо. Изменения хранятся в браузере. Подробнее о демо — раздел 15.

Оставьте окно PowerShell открытым, пока смотрите сайт. Чтобы остановить демо, вернитесь в это окно и нажмите Ctrl + C.

Вариант 2 Проверить магазин с сервером

Этот вариант проверяет настоящую серверную логику: вход, общие товары, заказы и тестовую оплату. На своём компьютере вместо PostgreSQL используется SQLite — база в одном файле backend/dev.db.

Шаг 1 Один раз установить нужные библиотеки

Библиотеки — готовые части программы, от которых зависит сервер. В терминале из папки проекта выполните по очереди:

python -m venv backend/.venv
.\backend\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt

Первая команда создаёт отдельную папку с Python для проекта — виртуальное окружение. Вторая скачивает и устанавливает библиотеки; для неё нужен интернет. Дождитесь окончания без сообщения об ошибке. Повторять установку нужно, если изменился список библиотек или удалена папка .venv.

Шаг 2 Запустить сервер в первом окне

В том же терминале выполните:

cd backend
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000

При первом запуске создаются база backend/dev.db, стартовые категории и локальный администратор. Когда сервер сообщит Application startup complete, оставьте окно открытым.

Данные локального администратора: admin@demo.kz / admin12345. Пароль отличается от пароля демо из варианта 1.

Письма локально не отправляются. Когда сайт попросит код подтверждения или сброса пароля, откройте backend/dev-mail.log обычным Блокнотом и найдите последнее письмо для нужной почты.

Шаг 3 Указать сайту адрес сервера

Откройте файл frontend/env.js в текстовом редакторе, например в Блокноте. Задайте строку и сохраните файл:

window.KBCH_API_URL = 'http://localhost:8000/api';

Этот адрес подходит только для проверки на своём компьютере. Перед публикацией нужен адрес вашего сервера или /api согласно инструкции размещения. Не отправляйте в репозиторий рабочие настройки с localhost.

Шаг 4 Запустить сайт во втором окне

Откройте ещё одно окно PowerShell из папки проекта. В нём должна быть видна папка с frontend, backend и deploy, а не сама папка backend.

python deploy/serve_frontend.py

Откройте http://localhost:5174. Вход администратора: http://localhost:5174/admin/. Пока сайт работает, оба окна PowerShell должны оставаться открытыми. Остановка каждого — Ctrl + C в соответствующем окне.

Шаг 5 При желании добавить примеры товаров

Новая база содержит категории, но товары нужно добавить. Можно создать свои товары в админ-панели или загрузить примеры. Для примеров откройте третье окно PowerShell из папки проекта:

.\backend\.venv\Scripts\python.exe demo/seed_backend.py

Команда предназначена для локальной демонстрации. После неё обновите страницу каталога. Не используйте заполнение примерами как обычный шаг запуска магазина с реальными данными.

Локальное описание API — адресов, по которым сайт обращается к серверу, — открывается по ссылке http://localhost:8000/api/docs.

Вариант 3 Открыть пустой сайт без сервера

В frontend/env.js задайте пустой адрес:

window.KBCH_API_URL = '';

Из папки проекта запустите:

python deploy/serve_frontend.py

Откройте http://localhost:5174. На чистом хранилище браузера товаров не будет. Чтобы управлять этой версией, впишите свою почту в список adminEmails файла frontend/js/config.js и зарегистрируйтесь с ней.

Этот режим сохраняет данные только в браузере. Он подходит для показа и подготовки содержимого. Защиту и общие данные настоящего магазина обеспечивает вариант с сервером.

Если что то не получилось

  • Открылся код или страница без оформления. Открывайте сайт по адресу http://localhost:…, а не двойным щелчком по HTML-файлу.
  • Сайт пишет, что сервер недоступен. Проверьте первое окно PowerShell и строку в frontend/env.js. У сайта и сервера разные порты: 5174 и 8000.
  • Администратор не входит. Для демо пароль admin123, для локального сервера — admin12345.
  • Адрес не открывается с телефона. Эти команды запускают просмотр только на компьютере. localhost на телефоне означает сам телефон. Обычную опубликованную версию можно открыть на любом устройстве.
  • Правки не появились. Сохраните файл и обновите страницу. Для локального просмотра используйте deploy/serve_frontend.py: он отключает кеширование и показывает свою страницу ошибки 404.

Команды выше предназначены для Windows PowerShell. На macOS и Linux Python окружения находится в backend/.venv/bin/python; из папки backend — в .venv/bin/python.

Для тестовой оплаты используйте только примеры из раздела 10. Как запускать автоматические проверки, описано в разделе 16.

3 Как устроен проект

Три основные части

У магазина есть видимая часть, программа на сервере и хранилище данных.

Фронтенд — видимая часть в браузере: страницы, фотографии, кнопки, корзина. Его файлы лежат в frontend/.

Бэкенд — программа на Python в папке backend/. Она проверяет вход и права, получает товары, оформляет заказы и отвечает сайту. Общение происходит через API: заранее заданные адреса и правила запросов. Например, запрос списка товаров и запрос создания заказа — разные действия API.

База данных — хранилище товаров, пользователей, отзывов и заказов. На своём компьютере по умолчанию используется файл SQLite. В рабочем магазине — PostgreSQL, отдельная программа для хранения данных.

Изменение цены или роли в браузере не меняет серверные данные само по себе. В режиме с сервером важные решения проверяет бэкенд. В режиме без сервера действует только локальная логика браузера.

Как оформляется заказ

  1. Покупатель заполняет контакты, доставку и способ оплаты, затем нажимает кнопку оформления.
  2. Сайт отправляет серверу номера товаров и количество. Цена, показанная в браузере, не считается надёжным источником.
  3. Сервер проверяет вход покупателя и данные формы, берёт цены и остатки из базы.
  4. Недоступные товары пропускаются. Если товара меньше, чем заказано, количество уменьшается до остатка. Если подходящих товаров нет, сервер отказывает в заказе.
  5. Сервер уменьшает остатки, рассчитывает доставку и итог. Это происходит при создании заказа, ещё до его оплаты.
  6. Покупатель получает номер заказа и инструкцию: перевод на Kaspi, оплата при получении или переход к тестовой оплате.

При размещении через Docker и Nginx запрос сначала принимает Nginx — программа, которая раздаёт файлы сайта, обеспечивает HTTPS и передаёт обращения /api/… бэкенду. HTTPS означает зашифрованное соединение с сайтом.

Что создаётся при работе

Часть файлов появляется после запуска и не должна попадать в репозиторий. Репозиторий — история исходных файлов проекта, которую ведёт Git.

  • backend/.venv/ — установленный Python и библиотеки проекта.
  • backend/dev.db — локальная база для проверки.
  • backend/dev-mail.log — письма с кодами в локальном режиме.
  • backend/media/ — загруженные фото при обычном локальном запуске.
  • deploy/.env — настройки сервера, в том числе пароли и ключи.
  • deploy/backups/ — резервные копии при размещении через Docker Compose.
  • .public/ — подготовленные публичные файлы сайта.

На сервере Docker загруженные фото и база хранятся в отдельных постоянных хранилищах — томах. Поэтому путь локальной папки и место хранения внутри контейнера могут различаться.

Файл .gitignore говорит Git, какие созданные файлы пропускать. Если секретный файл уже попал в историю Git, одного добавления в .gitignore недостаточно.

Почему файлы разделены именно так

Страницы используют общую точку работы с данными App.db. Она связывает их с хранилищем браузера или с API. Это упрощает повторное использование страниц, но режимы различаются по защите и хранению данных.

Большинство надписей отделено от логики и хранится в frontend/texts/ru/. Общие цвета и шрифты вынесены в frontend/css/base/variables.css. Правила для разных экранов собраны в frontend/css/responsive/.

Сервер разделён на папки по задачам: настройки, база, правила входных данных, сервисы и обработчики API. Эти папки помогают ориентироваться; они не обеспечивают полную независимость частей автоматически. Перед правкой нужно посмотреть, какие другие файлы использует нужный модуль.

Что есть на страницах

Общие элементы

Шапка — верхняя часть сайта: логотип, меню, поиск, избранное, вход и корзина. Подсказки поиска появляются после ввода двух символов. На небольшом экране меню открывается отдельной кнопкой.

Главная и каталог

На главной есть большой первый блок с фотографией, переход в каталог, карусели популярных и новых товаров, категории. Популярные товары выбираются по меткам «Хит» и «Популярное»; при их отсутствии используется доступный каталог. Новинки сначала берутся по метке «Новинка», затем список дополняется другими товарами по дате.

В каталоге есть категории, поиск, фильтры назначения, бренда и цены, сортировка и несколько вариантов показа. Стандартная порция — 12 товаров. Фильтры сохраняются в адресе страницы, поэтому ссылку на подборку можно передать другому человеку. На телефоне фильтры открываются отдельной панелью.

Карточка товара

Покупатель видит фотографии, цену, остаток, выбор количества и кнопку добавления в корзину. Ниже находятся описание, состав, применение, характеристики, дополнительные разделы владельца и отзывы.

Фотографии можно открыть крупно. Отзывы содержат оценку, текст, ответы магазина и голоса «Полезно». Чтобы оставить отзыв, нужен вход. Отметка «Покупка подтверждена» относится к проверке заказа сервером, а не к любой регистрации на сайте.

О нас доставка и оплата

На странице «О нас» находятся история магазина, ценности, показатели, контакты и блок из шести фотографий «Жизнь магазина». Фотографии этого блока можно менять в админ-панели и открывать на весь экран.

Страница доставки объясняет способы, сроки и стоимость доставки, оплату и частые вопросы. Её тексты лежат в frontend/texts/ru/delivery.js. После изменения реальных условий магазина проверьте также настройки расчёта доставки на сервере: текст страницы сам их не меняет.

Корзина и оформление

Корзина работает без входа. В ней можно менять количество и удалять товары. Недоступные товары помечаются; при создании заказа сервер повторно проверяет наличие и цены.

Оформление состоит из контактов, доставки и оплаты. Доставка: курьер, отправка по Казахстану или самовывоз. При работе с сервером список доступной оплаты приходит от него. После оформления показываются номер заказа и инструкция.

Тестовая оплата

Страница pages/pay.html показывает форму карты или имитацию Kaspi с QR-кодом и подтверждением. Это проверка сценария: деньги не списываются. Успешный тест меняет статус заказа на «Оплачен» внутри магазина. Использование этой страницы не подключает настоящий банк.

Вход и личный кабинет

Вход — по почте и паролю. При регистрации нужно подтвердить почту шестизначным кодом. Забытый пароль восстанавливается другим кодом из письма. В локальном запуске письма находятся в backend/dev-mail.log.

Личный кабинет содержит заказы и их статусы, свои отзывы, профиль и пароль. Имя и телефон можно менять. Почта показывается как данные аккаунта; обычного изменения почты в форме нет. Там же доступны смена пароля и удаление аккаунта. Для неоплаченных тестовых заказов есть переход к оплате, для заказов — повторное добавление товаров в корзину.

Избранное и ошибка 404

Избранное хранит товары, отмеченные сердечком. Вход не нужен; скрытые товары не показываются.

Страница 404 появляется по неверному адресу. В ней есть небольшой встроенный скрипт, который помогает правильно найти оформление даже для вложенного адреса. Если менять его код, нужно обновить разрешающий отпечаток в политике безопасности страницы и Nginx. Подробнее — раздел 9.

Технические подробности как устроен HTML файл

Внутри страницы есть две основные части. <head> хранит служебные настройки и подключения. <body> описывает видимое содержимое.

Страница подключает загрузчик js/app.js; атрибут data-page сообщает ему, какую логику загрузить. У страниц в pages/ относительный путь к файлам начинается с ../, потому что они находятся на один уровень глубже главной.

Метка вида data-t="about.title" означает: сюда нужно вставить текст с именем about.title из файлов переводов. Поэтому замена текста прямо между HTML-тегами может не дать ожидаемого результата: скрипт снова подставит значение по метке.

Как проверить правку

  1. Откройте сайт через локальный сервер из раздела 2.
  2. Проверьте обычное окно компьютера.
  3. В Chrome или Edge нажмите F12, затем Ctrl + Shift + M, чтобы включить режим устройств.
  4. Проверьте ширины около 360, 390, 768, 1024, 1280 и 1920 пикселей; телефон также поверните горизонтально.
  5. Убедитесь, что текст читается, кнопки доступны, блоки не накладываются и не появилась ненужная горизонтальная прокрутка.

Это ручная проверка. Автоматические проверки кода не доказывают, что страница хорошо выглядит на всех размерах.

Технические подробности порядок правил и публикация

Если несколько правил меняют одно свойство, результат зависит от приоритета селектора, !important и порядка подключения. При равном приоритете действует более позднее правило. Адаптация подключается после основных правил, чтобы уточнять их для нужного экрана.

При публикации deploy/prepare_frontend.py объединяет исходные CSS-файлы в .public/css/main.css и .public/css/admin.css, поправляя пути к изображениям. Это уменьшает число запросов к файлам. Править нужно исходники в frontend/css/, потому что следующая сборка заменит результат в .public/.

6 Работа кнопок и страниц JavaScript

Зачем нужен JavaScript

JavaScript, сокращённо JS, — язык программирования, который выполняется в браузере. В этом проекте он показывает товары, реагирует на кнопки, проверяет формы, ведёт корзину и обращается к серверу.

Файлы находятся в frontend/js/. Проект использует обычный JavaScript без React и Vue — дополнительных систем построения интерфейса. Для локального просмотра отдельная сборка JavaScript не нужна.

Этот раздел помогает найти нужный файл. Общие основы языка с примерами — раздел 19.

Что происходит при открытии страницы

  1. Браузер читает HTML и запускает frontend/js/app.js — загрузчик остальных файлов.
  2. Загрузчик читает frontend/env.js. Если адрес API не пустой, сайт запрашивает начальные данные у сервера по /bootstrap.
  3. Загружаются общие настройки, тексты, работа с данными и повторяющиеся элементы интерфейса.
  4. Подключаются файлы выбранной страницы. Её имя задано атрибутом data-page в HTML.
  5. core/start.js вставляет тексты, создаёт шапку и подвал, затем сообщает остальным частям, что можно начинать. Это сообщение называется событием app:ready.
  6. Код страницы показывает её содержимое.

Во время загрузки страница сначала скрывается; через шесть секунд скрытие снимается даже при задержке. Это ограничивает ожидание, но не исправляет ошибку, если один из необходимых файлов не загрузился.

7 Серверная часть Python

Что делает сервер

Бэкенд, или серверная часть, — программа, которая принимает запросы сайта, проверяет пользователя и данные, работает с базой и возвращает результат. Например: «этот пользователь может открыть заказ», «товара осталось две штуки», «сумма заказа такая».

Код написан на Python и находится в backend/app/. Основная библиотека — FastAPI. Библиотека — готовый набор возможностей, который использует программа.

Для обычного управления магазином менять этот код не нужно. Он понадобится, когда меняются правила работы: оформление, оплата, права, состав данных или проверка форм.

Как проходит запрос

Запрос приходит на адрес /api/…. Общий защитный слой проверяет размер и частоту обращений. Затем нужный обработчик проверяет вход, права и поля, читает или меняет базу, вызывает дополнительные сервисы и возвращает ответ.

Обработчик — функция для конкретного адреса и действия. Сервис — код отдельной задачи, например отправки письма или создания платежа. Схема данных — правила полей: что обязательно, какой тип, допустимая длина и формат.

8 База данных где лежат записи магазина

Главное для владельца

База данных хранит товары, покупателей, заказы и отзывы. SQLite — база в одном файле backend/dev.db для локальной проверки. PostgreSQL — отдельная программа хранения данных для рабочего сервера.

Тексты инструкций, исходный код и картинки из frontend/assets/images/ не являются базой. Загруженные через админ-панель фото тоже хранятся отдельно от неё. Поэтому полноценная резервная копия магазина должна содержать и базу, и загруженные фотографии.

Для повседневной работы используйте админ-панель. Ручное изменение таблиц нужно разработчику или администратору сервера, когда обычной формы недостаточно.

Таблица — набор однотипных записей. Например, одна строка в таблице товаров описывает один товар. Поле — отдельное значение строки: цена, название или остаток.

У товара цена, остаток и статус вынесены в отдельные поля. Описание, состав, применение, фотографии и дополнительные разделы собраны в поле data формата JSON — вложенный набор именованных значений. Это позволяет добавлять разделы описания без новой колонки для каждого из них.

В заказ записывается собственный список товаров с ценой и количеством на момент оформления. Позднее изменение цены товара не переписывает уже сохранённый состав заказа.

Входы коды и удаление

Сессия — сохранённый вход пользователя. По умолчанию она действует 30 дней. В базе хранится отпечаток токена входа, а не сама строка токена.

Код из письма по умолчанию живёт 10 минут. Разрешены пять попыток проверки; новый код можно запросить не раньше чем через минуту. Настройки можно изменить, поэтому эти числа относятся к значениям по умолчанию.

В модели PostgreSQL связи при удалении настроены так:

  • При удалении пользователя удаляются его сессии. Заказы и отзывы сохраняются без связи с аккаунтом.
  • При удалении товара удаляются его отзывы и голоса к ним.
  • При удалении отзыва удаляются его голоса «Полезно».

Удаление аккаунта не стирает автоматически контакты и состав старых заказов. Они сохранены как отдельная история заказов. Ограничение повторного голоса относится к сочетанию отзыва и идентификатора голосующего; оно не доказывает уникальность человека.

Как база помогает избегать ошибок

В таблицах есть ограничения — правила, которые база проверяет при сохранении. Например: цена и остаток неотрицательные, оценка отзыва от 1 до 5, статусы только из разрешённого списка, почта пользователя и адрес товара уникальны.

Есть индексы — дополнительные указатели для ускорения поиска по часто используемым полям. Это похоже на указатель в конце книги: он помогает быстрее найти нужную запись.

Запросы в текущем коде строятся через SQLAlchemy с параметрами: значение пользователя передаётся отдельно от текста команды базы. Новые запросы должны сохранять это правило.

Для PostgreSQL число одновременных подключений ограничено, а слишком долгий запрос по умолчанию прерывается через 15 секунд. Для облачного подключения можно включить шифрование DB_SSL=true. В схеме Docker Compose база находится во внутренней сети и не публикует порт в интернет.

Эти свойства описывают текущую реализацию. Они не отменяют необходимость проверять новые запросы и права доступа.

Миграция — файл с изменением структуры базы: создать таблицу, добавить поле или ограничение. История находится в backend/migrations/versions/.

Для локальной разработки команды выполняются в PowerShell из папки backend. Проверка соответствия моделей истории миграций:

После изменения app/db/models.py разработчик создаёт файл миграции:

.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "describe change"

describe change нужно заменить коротким описанием изменения. Автоматически созданный файл обязательно просматривают. Затем на подготовленной базе применяют:

.\.venv\Scripts\python.exe -m alembic upgrade head

Локальная база, созданная автоматически при первом запуске, может уже содержать таблицы без отметки миграций. Ошибку «таблица уже существует» нельзя исправлять повторным запуском вслепую: сначала проверьте состояние базы и историю Alembic. Не удаляйте базу с нужными данными.

Команда alembic downgrade -1 откатывает последнюю миграцию. Она может удалить поля и данные, поэтому не является универсальной кнопкой отмены.

Резервные копии

При работе через Docker Compose отдельный контейнер backup делает первую копию после запуска, затем повторяет примерно каждые 24 часа. В deploy/backups/ сохраняются файл базы kbch-…dump и архив фотографий media-…tgz.

По умолчанию копии старше 14 дней удаляются. Срок задаёт BACKUP_KEEP_DAYS. Копии нужно забирать за пределы сервера: файлы на том же диске не спасут при потере сервера.

Как сделать ручную копию и восстановить данные, описано в разделе 13. Сам факт наличия файла копии не подтверждает, что восстановление пройдёт: его нужно отдельно проверять.

9 Безопасность что защищено и что проверять

Главное для владельца

Настоящую проверку входа, прав, цен и заказов выполняет сервер. Режим без сервера и демо подходят для показа; их данные находятся в браузере пользователя.

В рабочем магазине защиту обеспечивают настройки веб-сервера, проверки Python и правила базы. Этот раздел объясняет реализованные меры. Он не является результатом отдельного полного аудита и не обещает отсутствие ошибок.

Практические задачи владельца: хранить секреты отдельно от исходников, использовать собственные пароли, проверять почту и резервные копии, устанавливать обновления осознанно.

Пароли и вход

В базе хранится хеш пароля — специальный проверочный отпечаток. При входе bcrypt сверяет введённый пароль с этим отпечатком. Открытого пароля в базе нет. Случайная добавка, называемая солью, делает отпечатки одинаковых паролей разными.

bcrypt намеренно замедляет перебор. Это усложняет подбор, но слабый пароль всё равно может быть угадан. Пользовательский пароль по умолчанию должен содержать не менее восьми символов; код также отклоняет распространённые и слишком простые пароли и некоторые варианты с именем почты.

После входа браузер получает случайный токен. В базе хранится его отпечаток SHA-256. Коды из писем хранятся в виде HMAC-отпечатков с секретом сервера; обычный срок кода — 10 минут, число попыток — пять.

Код: backend/app/core/security.py, backend/app/api/routers/auth.py.

Администратор

При рабочем размещении администратор задаётся настройками сервера: ADMIN_EMAIL и ADMIN_PASSWORD либо ADMIN_PASSWORD_HASH. Для открытого пароля требуется не менее 12 символов и отсутствие простых сочетаний из проверки конфигурации.

При каждом запуске сервер приводит выбранный аккаунт администратора к настройкам. У других аккаунтов роль администратора снимается. Удалить или заблокировать этот аккаунт через обычный интерфейс нельзя.

Вместо открытого пароля можно записать его bcrypt-хеш. Команда hash-password и место её запуска описаны в разделе 7. Полученное значение тоже нужно хранить как секрет.

Проверки прав и данных

Сервер проверяет роль на адресах управления магазином. Просто открыть страницу админ-панели или поменять вид кнопок в браузере недостаточно для серверных прав.

Сумма заказа вычисляется по ценам базы. При оформлении в PostgreSQL строки товаров блокируются на время изменения остатка, чтобы конкурирующие заказы не списали один и тот же остаток независимо друг от друга.

Тестовая оплата разрешена только владельцу заказа. Оплаченный, возвращённый или отменённый заказ повторно через тестовую форму не оплачивается. Настоящий перевод на Kaspi подтверждает администратор после проверки поступления денег.

Поля запросов проверяются на формат и длину. Текст очищается и экранируется: специальные символы выводятся как текст, чтобы введённая надпись не стала HTML-кодом. Такой подход снижает риск XSS — выполнения чужого скрипта на странице.

SQLAlchemy передаёт значения отдельно от команд базы. Это защищает реализованные запросы от SQL-инъекции — попытки превратить введённое значение в команду к базе. Новые запросы и новые места вывода текста должны сохранять эти правила.

Основные места: backend/app/api/deps.py, backend/app/schemas/, backend/app/core/sanitize.py, frontend/js/core/utils.js, backend/app/api/routers/orders.py.

Загруженные фотографии

Сервер проверяет допустимый размер и начало содержимого JPG, PNG или WEBP, затем сам придумывает имя файла. Это мешает принять произвольный файл только по расширению .jpg.

По умолчанию максимальный размер изображения — 8 МБ. Проверка сигнатуры не равна полной проверке содержимого и не является антивирусом. Код: backend/app/api/routers/catalog.py.

Защита соединения и браузера

При публикации через Nginx используется HTTPS — шифрование между браузером и сайтом. Специальные заголовки ограничивают поведение браузера:

  • Content-Security-Policy, или CSP: откуда разрешено загружать скрипты, стили, картинки и другие ресурсы.
  • Strict-Transport-Security: просьба к браузеру использовать HTTPS для следующих обращений.
  • X-Frame-Options: DENY и frame-ancestors 'none': запрет встраивания сайта в чужой фрейм.
  • X-Content-Type-Options: nosniff: запрет угадывать тип ответа вместо указанного.
  • Permissions-Policy: отключение доступа к камере, микрофону и геолокации для сайта.
  • Cache-Control: no-store: ответы API с личными данными не должны сохраняться в кеше.

CORS задаёт, с каких адресов сайта браузер может читать ответы API. Это дополнительное браузерное правило; оно не заменяет серверную проверку токена и прав.

Токен хранится в localStorage и передаётся явно через Authorization, а не автоматически в cookie. Это снижает обычный риск CSRF — отправки действия от имени пользователя с чужого сайта. Однако JavaScript своего сайта имеет доступ к токену, поэтому предотвращение XSS остаётся обязательным.

В frontend/404.html встроенный скрипт разрешён по точному хешу. После его изменения нужно обновить хеш в HTML и в deploy/nginx/headers.conf, иначе браузер заблокирует скрипт.

Секреты и публикация

deploy/.env содержит пароли и ключи. Его нельзя публиковать вместе с исходниками или отправлять как обычное приложение к инструкции. В рабочем запуске проверка конфигурации запрещает заведомо неподходящие настройки: слабый секрет, короткий открытый пароль администратора, SQLite вместо PostgreSQL, отсутствие нужной почты или неизвестный способ оплаты.

Для выдачи посетителям собирается папка .public/. Исходники Python, инструкции, .env, .git и резервные копии не должны раздаваться как содержимое сайта. Это обеспечивают сборка и настройки Nginx.

Если доверие к прокси включено, IP берётся из заголовка пересылки. Это безопасно только при правильной схеме, в которой запросы приходят через доверенный Nginx. Публиковать бэкенд в обход этой схемы без проверки настроек нельзя.

Что проверить перед началом продаж

  1. Проверка конфигурации не показывает ошибок рабочего режима.
  2. У администратора собственный пароль, а секреты не используются в других проектах.
  3. Письмо с кодом действительно приходит тестовому покупателю.
  4. Сайт открывается по HTTPS, а HTTP переводит на HTTPS.
  5. Создаются копии базы и фото; есть их экземпляр вне сервера.
  6. На сервере настроен доступ по SSH-ключу и открыты только нужные сетевые порты согласно разделу 13.
  7. В PAYMENT_METHODS оставлены только те способы, которые вы готовы показывать покупателям. Перед реальными продажами тестовые способы убраны.

Автоматические проверки описаны в разделе 16. Они проверяют конкретные сценарии; прохождение тестов не заменяет проверку настроек и реального пути покупателя.

10 Оплата

Главное какие способы действительно принимают деньги

Перевод на Kaspi показывает реквизиты владельца. Покупатель переводит деньги самостоятельно, а владелец проверяет поступление и вручную отмечает оплату.

Оплата при получении означает расчёт с курьером или при самовывозе. Магазин сам организует приём денег. Наличие способа в коде не выдаёт курьеру банковский терминал.

Тестовая карта и тестовый Kaspi только показывают процесс. Денег они не списывают, даже если заказ после проверки получил статус «Оплачен».

Kaspi Pay представлен в коде отдельным адаптером — частью для связи с платёжным провайдером. Его боевой адрес, форматы и правила ещё нужно сверить с условиями доступного вам сервиса и проверить. Готовность к реальному приёму денег не подтверждена самим наличием адаптера.

Где включаются способы оплаты

При размещении через Docker Compose откройте deploy/.env на сервере. Строка ниже — настройка файла, а не команда PowerShell:

PAYMENT_METHODS=kaspi_transfer,cash,test_card,test_kaspi

Имена разделяются запятыми. Покупателю показываются только включённые способы с заполненными обязательными настройками.

Готовность настроек видна в админ-панели: Настройки → Готовность к запуску. Из терминала можно запустить app.cli check по разделу 7. В рабочем режиме сервер откажется запускаться, если включён неизвестный способ или не хватает его обязательных полей.

После изменения deploy/.env примените настройки из папки проекта на сервере:

docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d backend

Затем обновите страницу оформления и проверьте список способов. Если используется другой хостинг, меняйте его переменные окружения и перезапускайте сервис по инструкции этого размещения.

Перевод на Kaspi действия владельца

В deploy/.env укажите настоящие реквизиты. Пример ниже содержит вымышленные данные:

KASPI_PHONE=+7 700 123 45 67
KASPI_RECEIVER=Имя получателя
KASPI_PAY_LINK=

KASPI_PHONE — номер для перевода, KASPI_RECEIVER — имя получателя, которое должен увидеть покупатель. Необязательное поле KASPI_PAY_LINK — ссылка для перехода к оплате, если она у вас есть. Пустое значение оставляет перевод по номеру.

  1. Покупатель оформляет заказ и видит номер, имя получателя, сумму и комментарий вида «Заказ №1001».
  2. Заказ получает статус оплаты «Ждёт оплаты». Инструкция также доступна в личном кабинете.
  3. Покупатель переводит деньги в своём приложении.
  4. Владелец проверяет поступление по своим операциям, открывает заказ в админ-панели и выбирает Оплата → Оплачен.

Сайт не проверяет банковский перевод автоматически. Сообщение или снимок экрана от покупателя сами по себе не меняют статус.

В локальном режиме вместо настоящих реквизитов подставлены +7 700 000 00 00 и «Магазин (тест)». Не используйте их для настоящей оплаты.

Оплата при получении

Дополнительные ключи не нужны. Заказ получает статус оплаты «При получении». После расчёта владелец вручную отмечает «Оплачен».

Текст интерфейса допускает карту через терминал курьера. Показывайте это обещание покупателю только если приём карт действительно организован. Сам сайт терминал и банковский эквайринг не подключает.

Как проверить тестовую оплату

Сначала оформите заказ с сервером и выберите тестовую карту или тестовый Kaspi. Сайт откроет pages/pay.html?order=…. Позже к этой странице можно вернуться из личного кабинета кнопкой «Перейти к оплате».

Для карты используйте примеры из таблицы, будущий срок, например 12/30, и CVC 123. CVC — короткий проверочный код карты; в тесте это вымышленные цифры.

Номер тестовой картыРезультат
4242 4242 4242 4242Успешная имитация оплаты
4000 0000 0000 0002Сообщение об отклонении, статус «Не прошла»
4000 0000 0000 9995Сообщение «Недостаточно средств»

На странице есть кнопки подстановки тестовых значений. Сервер проверяет математическую корректность номера по алгоритму Луна, формат срока и CVC. Это проверка формы данных, не обращение в банк. Полный номер и CVC в заказе не сохраняются; остаются последние четыре цифры в подписи тестовой оплаты. Вводить настоящую карту не нужно.

Для тестового Kaspi откройте имитацию приложения со страницы оплаты и нажмите «Подтвердить оплату» или «Отменить». QR-код и экран здесь являются частью показа, а не подключением к приложению банка.

После успеха статус заказа станет «Оплачен» в кабинете и админ-панели. Такой заказ учитывается как оплаченный внутри магазина, хотя денег не было. Поэтому проверочные заказы нужно отличать от настоящих при разборе продаж.

Что ограничено

Оплатить тестом можно только свой заказ с выбранным тестовым способом. Повторная оплата уже оплаченного или возвращённого заказа запрещена. Отменённый заказ оплатить нельзя. После удаления test_card и test_kaspi из PAYMENT_METHODS тестовая оплата перестаёт работать.

Перед приёмом реальных заказов уберите тестовые способы. Пример для ручных расчётов:

PAYMENT_METHODS=kaspi_transfer,cash

Статус заказа и статус оплаты разные поля

Статус заказа описывает обработку и доставку: новый, в работе, отправлен, завершён или отменён. Статус оплаты описывает деньги:

Технические подробности подключение Kaspi Pay

Этот подраздел нужен разработчику. До включения адаптера получите договор и документацию доступного платёжного сервиса. Проверьте, что вам действительно выданы нужные доступы: их получение и совместимость текущего кода не гарантированы.

В backend/app/services/payments/kaspi_pay.py реализован следующий ожидаемый контракт:

  • start() отправляет запрос на <KASPI_API_URL>/invoices с Bearer-ключом. Передаются merchantId, orderId, целая сумма в тенге, currency, описание, адрес возврата и адрес уведомления.
  • Ответ должен содержать идентификатор счёта и ссылку HTTPS на оплату; поддержаны имена invoiceId/id и paymentUrl/url.
  • Адрес уведомлений: https://ВАШ-ДОМЕН/api/payments/kaspi/webhook. Webhook — автоматическое сообщение платёжного сервиса вашему серверу.
  • check_signature() проверяет HMAC-SHA256 исходного тела сообщения с секретом; подпись ожидается в заголовке X-Signature.
  • parse_webhook() разбирает orderId, status и целую сумму amount.

Адрес, авторизация, поля и подпись должны точно соответствовать реальному провайдеру. До подтверждения совместимости не включайте kaspi_pay покупателям. Подробный формат текущей реализации — раздел 24.

В обработчике уведомлений неверная подпись отклоняется. Для сообщения об успехе сумма сверяется с заказом. Повторное сообщение для уже оплаченного или возвращённого заказа не меняет его снова. При выключенном kaspi_pay адрес уведомления возвращает 404.

После сверки и доработки настройте KASPI_API_URL, KASPI_MERCHANT_ID, KASPI_API_KEY, KASPI_WEBHOOK_SECRET, адреса сайта и API. Проведите проверки в среде провайдера, затем контролируемую проверку реального расчёта по согласованной процедуре.

Технические подробности файлы и новый способ

Способы находятся в backend/app/services/payments/: cash.py, kaspi_transfer.py, sandbox.py, kaspi_pay.py. Общие правила — в base.py, список способов METHODS — в __init__.py.

Разработчик добавляет отдельный класс способа с кодом, заголовком, требованиями к настройкам, запуском start() и инструкцией instructions(). Затем регистрирует его в METHODS, добавляет поля в backend/app/core/config.py и тесты его реального контракта. Для автоматических уведомлений нужен обработчик с проверкой подписи, суммы и повторов.

Сайт уже получает список способов от сервера. Существующий формат инструкции может подойти без новых элементов страницы; иной платёжный сценарий потребует доработки интерфейса. Простого копирования файла старого провайдера недостаточно для безопасного подключения нового.

Тестовый обработчик расположен в backend/app/api/routers/orders.py, проверка карты — в sandbox.py, интерфейс — в frontend/pages/pay.html, frontend/js/pages/pay.js и frontend/css/pages/pay.css.

Сначала выполните полное обновление страницы. Если браузер продолжает брать старые файлы, разработчику нужно согласованно изменить VERSION в frontend/js/app.js и номера ?v= в подключениях HTML. В исходной версии используется 23: при следующем обновлении выбирайте новый общий номер. Не заменяйте все числа 23 по проекту: менять нужно только номера версии ресурсов. Затем заново соберите .public/.

Скорость автолистания каруселей задаёт INTERVAL в frontend/js/components/carousel.js в миллисекундах. Длительности переходов находятся в frontend/css/components/transitions.css, других анимаций — в frontend/css/components/motion.css. После изменений проверяйте, что интерфейс остаётся удобным на телефоне.

13 Опубликовать магазин в интернете

Публикация — размещение сайта на постоянно работающем сервере. После неё покупатели открывают магазин по общему адресу, а товары, аккаунты и заказы сохраняются в общей базе.

Для первого запуска пригодится человек, который умеет подключаться к серверу и настраивать домен. Владельцу важно подготовить контакты, реквизиты, каталог и проверить результат по главе 14.

Выбрать вариант размещения

ВариантДля чего подходит
VPS с DockerРабочий магазин на своём арендованном сервере; основной сценарий этой главы
RenderРабочий магазин на управляемом хостинге; настройки задаются в его панели

Свой компьютерПодготовка и проверка; запуск описан в главе 2

VPS — арендованный компьютер в интернете. Docker запускает программы проекта в отдельных окружениях, которые здесь называются контейнерами. Команды ниже относятся к Ubuntu на VPS. Их вводят в терминале после подключения к серверу по SSH, а не в PowerShell своего компьютера.

Что подготовить для VPS

  • Сервер с Docker Engine и Compose v2, Git и Python 3.11 или новее. Ориентир для начала — 2 ГБ оперативной памяти; нагрузка и объём каталога влияют на требования.
  • Домен магазина. В его DNS, то есть настройках привязки имени к серверу, основной домен и www должны указывать на VPS. Неверные IPv6-записи тоже могут мешать открытию сайта.
  • Открытые входящие порты 80 и 443 для сайта. PostgreSQL наружу открывать не нужно.
  • Почту с рабочими настройками SMTP — отправки писем приложением. У хостера должна быть разрешена исходящая отправка на нужный почтовый порт.
  • Доступ к репозиторию проекта и отдельное место для копий базы и фотографий вне VPS.

Программы устанавливайте по инструкции поставщика сервера и Docker. Не продолжайте запуск, пока docker compose version, git --version и python3 --version не выполняются без ошибки.

Шаг 3 Включить HTTPS и запустить программы

HTTPS шифрует соединение с сайтом. Первая команда получает сертификат для домена и www; в этот момент порт 80 должен быть свободен:

docker compose --env-file deploy/.env -f deploy/docker-compose.yml --profile init run --rm --service-ports certbot-init
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec web nginx -t

При запуске API проверяет настройки и обновляет структуру базы. Дождитесь готовности backend. Если контейнер постоянно перезапускается, прочитайте причину:

docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs --tail=100 backend

После успешного запуска добавьте стартовые категории:

docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec backend python -m app.cli seed --frontend /frontend

Эта команда добавляет категории, а не демо-товары. Реальные товары загрузите через админ-панель.

Результат: сайт открывается по https://ВАШ-ДОМЕН, панель — по адресу /admin/index.html. Теперь выполните проверку письма, заказа и резервных копий по главе 14. Открывающейся главной страницы недостаточно для готовности магазина.

В обычном режиме работают пять сервисов: db хранит базу; backend обрабатывает действия; web отдаёт сайт; certbot продлевает сертификат; backup копирует базу и фото. certbot-init нужен отдельно для первоначального выпуска сертификата.

Обновить сайт или пароль администратора

14 Проверить запуск и сохранить данные

Эта глава — список приёмки рабочего магазина и инструкция по резервным копиям. Время запуска зависит от готовности сервера, домена, почты и каталога. Фиксированного срока здесь нет.

Сначала разместите магазин по главе 13. Проверяйте адрес рабочего сервера в приватном окне браузера: отдельная демо-версия не подтверждает готовность настоящего магазина.

Проверить магазин перед приёмом покупателей

Зачем: убедиться, что покупатель сможет войти, заказать товар и получить правильную сумму.

  1. Откройте домен. HTTP должен переводить на HTTPS, www — на основной адрес; предупреждения о сертификате быть не должно. Адрес /api/health должен показать {"status":"ok"}.
  2. Войдите администратором. Создайте реальный товар с фото, ценой и остатком. Измените цену, скройте товар и верните публикацию. Проверьте каталог на компьютере и телефоне.
  3. Зарегистрируйте покупателя на отдельной почте. Получите настоящее письмо, подтвердите адрес, войдите и выйдите. Проверьте восстановление пароля. В рабочем режиме код из демо не подходит.
  4. Соберите корзину и оформите проверочный заказ с оплатой при получении. Убедитесь, что состав, количество, доставка и итог правильные. У покупателя виден его заказ, у администратора — тот же номер.
  5. Измените состояние заказа в панели и обновите кабинет покупателя. Отмените проверочный заказ и убедитесь, что остаток вернулся. Отмена не переводит деньги через банк.
  6. Если отдельно проверяете test_card, делайте это до открытия магазина покупателям. После проверки удалите test_card,test_kaspi из PAYMENT_METHODS, пересоздайте API и проверьте список способов оплаты ещё раз. Настоящую онлайн-оплату проверяют по правилам провайдера отдельно.
  7. Перезапустите API штатной командой и убедитесь, что товар и загруженное фото сохранились. В панели «Настройки» проверьте «Готовность к запуску».
  8. Выйдите из аккаунта. Адрес /api/admin/users должен отказать в доступе. Адреса /.env, /backend/.env, /.git/config не должны показывать содержимое файлов.

Результат: письмо приходит, заказ проходит, данные остаются после перезапуска, закрытые сведения недоступны гостю. Если обязательный шаг не прошёл, завершите исправление до приёма покупателей.

Проверить автоматические копии на VPS

Полная копия магазина состоит минимум из базы и загруженных фото. В Docker их сохраняет сервис backup: при старте, затем примерно каждые 24 часа. На диске VPS результаты лежат в deploy/backups/:

  • kbch-ДАТА_ВРЕМЯ.dump — база;
  • media-ДАТА_ВРЕМЯ.tgz — фотографии с той же отметкой времени.

Команды выполняйте в терминале Ubuntu на VPS из корня проекта:

docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs --tail=20 backup
ls -lh deploy/backups/

Результат: в журнале есть сообщение backup: ... (database + media), а в папке — оба непустых файла. backup FAILED означает, что новая пара не создана. По умолчанию копии старше 14 дней удаляются; срок задаёт BACKUP_KEEP_DAYS.

Копируйте пары во внешнее защищённое хранилище: при потере диска сервера локальные копии тоже пропадут. Отдельно сохраните deploy/.env в защищённом месте и отметьте версию кода. В архивах базы и фото этого файла нет. Выгрузка JSON из админ-панели не заменяет такую копию.

Снять копию перед обновлением

Зачем: иметь согласованные базу и фото на один момент. Автоматическое копирование не останавливает изменение данных, поэтому перед важным обновлением используйте короткую остановку API.

  1. Запишите рабочую версию кода:
git rev-parse HEAD
  1. Убедитесь, что имена kbch-before-update.dump и media-before-update.tgz ещё не заняты нужными копиями. Для следующего обновления выберите новые имена, например с датой, во всех командах.
  2. Остановите приём действий, создайте пару и проверьте читаемость архивов:
docker compose --env-file deploy/.env -f deploy/docker-compose.yml stop backend
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T backup sh -c 'umask 077; pg_dump -Fc -f /backups/kbch-before-update.dump && tar czf /backups/media-before-update.tgz -C /media . && pg_restore --list /backups/kbch-before-update.dump >/dev/null && tar tzf /backups/media-before-update.tgz >/dev/null'
docker compose --env-file deploy/.env -f deploy/docker-compose.yml start backend

Если средняя команда завершилась ошибкой, не считайте копию готовой. Выполните последнюю команду, чтобы вернуть API в работу, и исправьте причину. При успехе скопируйте пару за пределы VPS до обновления.

Проверка списка архива подтверждает читаемость, но не успешное восстановление. Сопровождающий должен заранее восстановить пару в отдельную тестовую базу и отдельное хранилище фото, затем открыть товар, фото и заказ. Для этой проверки рабочую базу не очищают.

Восстановить после неудачного обновления

Это заменяет данные магазина. Заказы и изменения после даты выбранной копии могут пропасть. Перед восстановлением согласуйте с владельцем время остановки и конкретную пару; сохраните текущие данные отдельно.

Если структура базы не менялась, может быть достаточно вернуть записанный рабочий коммит, собрать .public/ и заново запустить контейнеры по главе 13. Если обновление уже изменило структуру базы, возврата кода может быть недостаточно: сопровождающий возвращает совместимую версию и восстанавливает выбранную пару.

Ниже пример именно для пары before-update и Docker на VPS. Убедитесь, что оба файла находятся в deploy/backups/ и относятся к нужной дате:

docker compose --env-file deploy/.env -f deploy/docker-compose.yml stop backend
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T backup sh -c 'pg_restore --exit-on-error --clean --if-exists -d "$PGDATABASE" /backups/kbch-before-update.dump'
docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm --no-deps --user root --entrypoint sh -v "$PWD/deploy/backups:/restore:ro" backend -c 'tar xzf /restore/media-before-update.tgz -C /app/media && chown -R app:app /app/media'
python3 deploy/prepare_frontend.py
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build

При ошибке восстановления не переходите к открытию магазина: выясните причину. Распаковка фото дополняет или заменяет файлы, но не удаляет лишние файлы из хранилища. После успеха повторите проверку входа, товара, фотографий и заказа.

Не применяйте docker compose down -v для обычного перезапуска: ключ -v удаляет постоянные хранилища, включая базу, фото и сертификаты.

Что передать владельцу

Сохраните адрес сайта и панели, рабочую версию кода, дату приёмки, место внешних копий и контакт сопровождающего. Доступы храните в менеджере паролей. Для Render выполните тот же список приёмки, но копии и откат настройте средствами его базы и диска: команды Docker выше относятся к VPS.

16 Как проверить что изменения работают

Тест — программа, которая сравнивает результат с ожидаемым. Например, проверяет, что заказ рассчитывается по цене сервера. Наличие тестов в папке не означает, что они прошли: результат относится к конкретному запуску и версии проекта.

Для правки текста руководства не нужно запускать серверные тесты. Для изменения программы выбирайте наборы, которые проверяют затронутое поведение. После изменения оформления обязательно посмотрите страницы в браузере.

Подготовить проверку на Windows

Что открыть: PowerShell в корне проекта. В этой папке видны backend, frontend, tests и demo.

Понадобятся Python 3.11 и Node.js 20 — версии, используемые автоматическими проверками проекта. Проверить наличие:

python --version
node --version

Если виртуального окружения ещё нет, создайте его. Это отдельная папка с пакетами проекта:

python -m venv backend/.venv

Установите закреплённые зависимости и проверьте их совместимость:

& .\backend\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
& .\backend\.venv\Scripts\python.exe -m pip check

Результат: установка завершена, pip check сообщает No broken requirements found. Активировать окружение отдельной командой не нужно: команды ниже явно запускают Python из этой папки. На Linux и macOS аналогичный путь — backend/.venv/bin/python.

Проверить сайт сборку и демо

Из корня проекта в PowerShell:

$testFiles = Get-ChildItem -LiteralPath tests/frontend -Filter *.test.cjs
node --test $testFiles.FullName
& .\backend\.venv\Scripts\python.exe -m pytest tests/general -q
& .\backend\.venv\Scripts\python.exe -m pytest demo/tests -q

Результат: каждый запуск завершается без ошибок; в отчёте нет failed или error. Число случаев может меняться при развитии проекта. Тесты сборки используют временные каталоги.

Чтобы отдельно найти ошибки синтаксиса во всех файлах JavaScript:

Get-ChildItem frontend -Recurse -Filter *.js | ForEach-Object {
  node --check $_.FullName
  if ($LASTEXITCODE -ne 0) { throw "Ошибка синтаксиса: $($_.FullName)" }
}

Отсутствие ошибок здесь означает лишь, что код удалось разобрать. Это не проверка изображения страницы и всех действий пользователя.

Проверить API в отдельной тестовой базе

Важно: серверные тесты удаляют и создают таблицы перед сценариями. В TEST_DATABASE_URL нельзя указывать рабочую базу или базу с нужными данными.

Для обычной локальной проверки оставьте эту переменную пустой: тогда тесты создадут временную SQLite. Выполните из корня проекта:

$env:TEST_DATABASE_URL = ''
Set-Location backend
& .\.venv\Scripts\python.exe -m pytest -q
Set-Location ..

Результат: серверные проверки прошли, а PowerShell снова находится в корне проекта. После ошибки тестов также выполните Set-Location .., прежде чем запускать команды для корня.

Для одного сценария из папки backend:

& .\.venv\Scripts\python.exe -m pytest tests/test_order_scenarios.py -q

Для списка случаев без выполнения используйте -m pytest --collect-only -q. Зависимости всё равно нужны: подготовка тестов импортирует приложение.

SQLite удобна локально, но не воспроизводит все особенности одновременной работы PostgreSQL. Для проверки PostgreSQL выделяют отдельную одноразовую базу и задают её адрес через TEST_DATABASE_URL. При этом письма и платёжный провайдер в тестах подменяются. Настоящую SMTP-отправку и оплату проверяют отдельно.

17 Частые вопросы и короткие ответы

Эта глава помогает быстро разобраться в магазине и объяснить проект. Для выполнения действий переходите в указанную главу: там есть шаги и ожидаемый результат. Незнакомые слова — в словаре.

Работа с магазином

Можно читать документацию без Visual Studio Code

Да. Готовое руководство в Word открывается отдельно от проекта, в том числе на телефоне. Редактор кода нужен только для изменения исходных файлов сайта. Работать с товарами и заказами можно в обычном браузере через админ-панель.

Чем демо отличается от рабочего магазина

Демо хранит примерные данные в вашем браузере, имитирует письма и оплату. В рабочем режиме API сохраняет общие товары, пользователей и заказы в базе на сервере. Проверка демо не подтверждает работу настоящей почты и оплаты. Глава 15.

Почему изменённый товар не появился у другого человека

Проверьте адрес сайта и режим. В демо и в режиме без API изменения локальны для браузера. В серверном режиме проверьте, что товар сохранён, выбран вариант «На сайте», а другая страница обновлена. Главы 2 и 11.

Для чего покупателю нужна регистрация

Каталог, товары, отзывы и корзина доступны гостю. Для оформления заказа, кабинета и написания отзыва нужен вход. В рабочем режиме регистрация подтверждается кодом из письма, затем вход выполняется по почте и паролю. Вход через Google и вход только по коду не реализованы.

Почему письмо с кодом не приходит

В демо письма не отправляются. При локальном API с исходными настройками код печатается в журнал сервера. На рабочем сайте нужны правильно настроенные SMTP и отправитель; проверьте также «Спам». Если код истёк, запросите новый после установленной паузы. Главы 2 и 13.

Как войти администратором

На рабочем сайте используйте доступы, заданные при настройке сервера. У локального API и отдельного демо разные исходные пароли. Все варианты входа собраны в начале главы 11.

Можно поменять все тексты в админ панели

В панели меняются товары, категории, заказы, отзывы, пользователи и шесть фото «О нас». Надписи интерфейса, контакты и оформление меняются в файлах. Глава 12.

Где хранится корзина

В браузере покупателя, в localStorage. Корзина переживает обычное закрытие вкладки, но не обязана появляться в другом браузере или на другом устройстве. На сервер её содержимое передаётся при оформлении заказа.

Что происходит если товара не хватает

API заново проверяет наличие. Недоступные позиции пропускаются, количество ограничивается остатком. Если доступных товаров не осталось, заказ не создаётся. Поэтому после оформления проверьте итоговый состав. PostgreSQL блокирует изменяемые строки во время оформления, чтобы согласовать одновременные покупки; локальная SQLite не проверяет все те же гарантии.

Можно изменить цену заказа через браузер

API берёт цены из своей базы и считает доставку по своим настройкам. Переданные покупателем поддельные суммы не задают стоимость заказа. После оформления в заказе сохраняется состав и цена на тот момент. Главы 8 и 24.

Как принимается перевод на Kaspi

После заказа покупатель видит реквизиты и сумму. Владелец проверяет поступление в банке и вручную отмечает «Оплачен» в панели. Это отличается от автоматического подтверждения банковским сервисом. Глава 10.

Тестовая карта действительно снимает деньги

Нет. test_card и test_kaspi — имитация. Успешная проверка может поставить заказу отметку «Оплачен», хотя настоящего платежа нет. Перед открытием магазина эти способы убирают из настроек. Для проверки используют только тестовые реквизиты из главы 10.

Достаточно включить kaspi_pay чтобы заработала онлайн оплата

Нет. В проекте есть адаптер — код связи с провайдером. Перед включением нужно подтвердить доступ к API, проверить реальные адреса, поля запросов, подпись уведомлений и все результаты платежа в среде провайдера. Наличие заполненных ключей само по себе не доказывает готовность подключения.

Отмена заказа возвращает деньги

Отмена возвращает товар в остаток и меняет состояние записи. Банковский возврат сама панель не выполняет. Удаление заказа также не заменяет отмену: удаление не возвращает товар на склад. Глава 11.

Экспорт JSON полноценная резервная копия

Нет. Он выгружает часть данных, но не аккаунты и не сами загруженные фото. Для восстановления нужна пара базы .dump и фотографий .tgz, версия кода и сохранённые настройки. Копии следует хранить вне сервера. Глава 14.

Можно разместить рабочий магазин на GitHub Pages

GitHub Pages в этом проекте используется для демо. API и PostgreSQL там не запускаются. Для рабочего магазина предусмотрены VPS с Docker либо Render. Глава 13.

Как объяснить устройство проекта

Из каких частей состоит проект

HTML задаёт содержимое страниц, CSS — оформление, JavaScript — действия в браузере. Python и FastAPI обрабатывают запросы на сервере. PostgreSQL хранит рабочие данные. Браузер и сервер обмениваются запросами через API. Глава 3.

Почему здесь нет React или Vue

Текущий интерфейс написан на обычном JavaScript. Файл app.js подключает модули, App.db даёт общий способ работы с данными, повторяемые части интерфейса вынесены в компоненты. Это выбор реализации проекта, а не гарантия большей скорости любого сайта. Глава 6.

Что делает FastAPI

Это библиотека для серверного приложения на Python. Она связывает адрес запроса с обработчиком и проверяет входящие данные по схемам. Справочник API доступен по /api/docs, только когда включён DOCS_ENABLED; в рабочем режиме он обычно выключен. Глава 7.

Для чего SQLAlchemy и Alembic

SQLAlchemy помогает читать и менять базу из Python. Alembic хранит последовательность изменений структуры таблиц — миграции. Контейнер API применяет их при запуске. Обратная миграция не заменяет резервную копию и не обязана вернуть удалённые данные. Глава 8.

Как хранятся пароль и вход пользователя

В серверной базе хранится хеш пароля, а не исходный пароль. После входа браузер получает случайный токен и передаёт его с запросами. В базе хранится отпечаток токена; выход и блокировка позволяют прекратить доступ. Демо использует упрощённое локальное хранение и не является образцом защиты рабочего магазина. Глава 9.

Кто решает что пользователь администратор

API проверяет сессию и роль при каждом закрытом запросе. Отсутствие кнопки или скрытая ссылка сами по себе не защищают данные. Рабочего администратора задают серверными настройками; покупатель не может назначить себе роль в запросе.

Какие меры защиты предусмотрены

Проверка входных данных, параметризованные запросы к базе, безопасный вывод текста, ограничения ссылок и загрузок, HTTPS, защитные заголовки и ограничения частоты запросов. Эти меры уменьшают определённые риски, но не доказывают отсутствие всех уязвимостей. Ограничение запросов не заменяет внешнюю защиту от крупной распределённой перегрузки. Глава 9.

Почему интерфейс подходит для телефона

CSS содержит отдельные правила для разных размеров экрана: меню и фильтры перестраиваются, элементы располагаются удобнее для узкого экрана. Фактический результат проверяют на нужных страницах и устройствах. Глава 5.

Что сделано для скорости и качества

При публикации стили объединяются, Nginx сжимает и кеширует подходящие файлы, начальные данные загружаются через /api/bootstrap. Есть отдельные тесты логики, API и сборок. Скорость и корректность конкретной версии подтверждаются измерением и проверкой, а не списком технологий. Глава 16.

Что ещё можно добавить

Например, проверенную онлайн-оплату, уведомления владельцу о заказе, аналитику, казахский язык, внешнее хранилище фотографий. Это направления дальнейшей разработки, а не уже работающие возможности. Уведомления в Telegram и готовая банковская интеграция не следует обещать без отдельного подключения.

Кто за что отвечает

Представьте карточку товара. HTML сообщает браузеру: «Здесь название, фотография и кнопка». CSS задаёт цвет, размер и расположение. JavaScript реагирует на кнопку и добавляет товар в корзину. Когда покупатель оформляет заказ, Python на сервере проверяет данные, считает сумму и сохраняет заказ в базе.

HTML из чего состоит страница

Тег обозначает элемент: заголовок, кнопку, картинку. Атрибут уточняет его свойства. Например, у ссылки href хранит адрес перехода.

<button type="button" class="example-button" id="buy-button">
  В корзину
</button>

Здесь button — кнопка, type="button" — обычное действие без отправки формы. class связывает кнопку с оформлением, id помогает найти именно эту кнопку в коде. Надпись между тегами увидит покупатель. Это учебный пример, его не нужно добавлять на сайт.

  • ?slug=cream: передать параметр в адресе.
  • #orders: перейти к нужному разделу интерфейса.

CSS как задаётся внешний вид

.example-button {
  color: white;
  background: var(--primary);
  padding: 12px 20px;
  border-radius: 12px;
}

Точка перед example-button означает: «Применить оформление ко всем элементам с таким классом». Внутри скобок перечислены свойства. color — цвет текста, background — фон, padding — внутренний отступ, border-radius — скругление. var(--primary) берёт общий цвет из frontend/css/base/variables.css.

Если ширина окна не больше 760 пикселей, кнопка займёт всю доступную ширину.

Иногда один элемент подходит под несколько правил. Браузер выбирает правило по каскаду: учитывает источник, точность селектора, !important и порядок. Если остальные условия одинаковые, побеждает более позднее правило. Поэтому одного переноса строки ниже бывает недостаточно для исправления стиля.

23 Переменные окружения все настройки сервера

Эта глава — справочник для человека, который запускает или обслуживает API. Переменная окружения — именованная настройка, которую программа получает при запуске. Например, COURIER_PRICE=1000 задаёт стоимость курьера. Менять Python-код ради этого не нужно.

Настройки описаны в backend/app/core/config.py, в классе Settings. Здесь перечислены их имена, значения при отсутствии настройки и назначение. Настоящие пароли и ключи в документацию не включаются.

Как выглядит настройка

В .env одна строка задаёт одно значение:

ENVIRONMENT=production
COURIER_PRICE=1000
DOCS_ENABLED=false

true означает «включено», false — «выключено». Списки, например способы оплаты, записываются через запятую. Это пример формата, а не готовый полный файл для рабочего сервера. Образец полного набора — deploy/.env.example.

Откуда приложение берёт значения

При обычном запуске приоритет такой, от самого высокого к самому низкому:

  1. Переменные запущенного процесса.
  2. Файл backend/.env.
  3. Файл .env в текущей рабочей папке.
  4. Значения из Settings.

Если оба пути .env указывают на один файл, это один источник. Для любого режима, кроме точного ENVIRONMENT=production, программа дополнительно подставляет локальные значения там, где они оставлены пустыми: SQLite, учебного администратора, журнал писем и реквизиты-примеры.

API сам не ищет deploy/.env. При Docker-запуске Compose читает его для подстановок через --env-file и передаёт backend через env_file. Поля из environment в Compose важнее значений env_file. На Render настройки задаются в панели хостинга.

После изменения нужен перезапуск процесса. Для Docker после правки deploy/.env пересоздайте backend командой из корня проекта:

docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d backend

Обычный restart запускает тот же контейнер с прежним окружением и не применяет новые значения.

24 API адреса запросов и данные

Эта глава нужна разработчику, который связывает сайт с сервером или ищет причину ошибки запроса. Обычный пользователь управляет магазином через страницы и админку; отправлять эти запросы вручную ему не требуется.

API — набор адресов для получения и изменения данных. Например, браузер отправляет запрос «создай заказ», а сервер отвечает номером, составом и суммой. HTTP задаёт способ обмена запросами. JSON — текстовый формат данных внутри запроса и ответа.

Все адреса начинаются с /api. Код запросов находится в backend/app/api/routers/, правила полей — в backend/app/schemas/, преобразование записей базы в ответы — в backend/app/api/serializers.py.

Локально интерактивное описание открывается по адресу http://localhost:8000/api/docs, его JSON-схема — /api/openapi.json. В production они по умолчанию выключены. Уведомление Kaspi не включено в эту схему и описано отдельно ниже.

Как прочитать запрос

POST /api/auth/login HTTP/1.1
Content-Type: application/json

{"email":"buyer@example.com","password":"пароль локального аккаунта"}

Этот пример означает: отправить email и пароль в адрес входа. Учебный адрес и пароль нужно заменить данными своего локального аккаунта. По умолчанию локальный сервер находится на http://localhost:8000.

После входа сервер возвращает token. Для защищённого запроса клиент передаёт заголовок Authorization: Bearer <token>. Это случайный ключ сессии, а не JWT. В базе хранится его SHA-256-отпечаток и срок действия, в браузере исходный токен хранится в localStorage.

Параметры адреса идут после ?, например /api/products?all=1. Текст параметров нужно кодировать через URLSearchParams или encodeURIComponent. В JSON-запросе нужен Content-Type: application/json. В текущем клиенте эту работу выполняет request() из frontend/js/store/remote.js.

В таблицах «пользователь» означает вошедший и допущенный сервером аккаунт. «Админ» — дополнительная проверка роли admin. Запись в фигурных скобках, например {product_id}, заменяется настоящим ID. Знак ? после имени поля означает, что поле необязательное; сам знак в JSON не добавляется.

Тестовая оплата

Sandbox — имитация без списания денег. Принимается SandboxPayIn: action — pay или cancel, card — до 23 символов, expiry — MM/YY, cvc — до 4 цифр. Для тестовой карты дополнительно проверяются номер, срок и CVC; действие cancel используется тестовым Kaspi. Примеры — в главе 10.

Оплата доступна владельцу заказа с включённым тестовым способом. Оплаченный, отмеченный возвращённым или отменённый заказ повторно оплатить этим запросом нельзя. Реальные реквизиты карты в тестовую форму не вводят.

Внешнее уведомление Kaspi

Webhook — запрос, который платёжный сервис сам отправляет магазину. Реализованный код ждёт X-Signature: HMAC-SHA256 в шестнадцатеричном виде от исходного тела запроса с ключом KASPI_WEBHOOK_SECRET.

В JSON ожидаются orderId, status и amount. Статусы paid/success/completed считаются успешными. Сумма — целое неотрицательное число или строка цифр, совпадающая с total заказа. Для уже paid/refunded повтор возвращает ok. Неуспешный статус отмечает failed.

Это описание контракта текущего кода. Его нужно подтвердить у провайдера перед боевым подключением; само наличие маршрута не подтверждает работающую банковскую интеграцию.

25 Сборка обновление и сопровождение

Эта глава нужна человеку, который публикует магазин и затем поддерживает сервер. Первую публикацию выполняйте по главе 13 или главе 14. Здесь объясняется, что происходит при сборке и как обновлять уже работающий проект.

Сборка готовит файлы для посетителей. Развёртывание, или deploy, размещает их на сервере и запускает приложение. В этом проекте Python готовит витрину, Docker упаковывает API, а Compose запускает базу, API и остальные сервисы вместе.

Что делает сборщик витрины

deploy/prepare_frontend.py выполняет следующие действия:

  1. Проверяет папку frontend/ и путь результата, чтобы не заменить постороннюю папку.
  2. Готовит временную папку в корне проекта.
  3. Копирует разрешённые файлы из pages, admin, css, js, texts и assets, а также разрешённые корневые файлы.
  4. Исключает служебные и скрытые папки, ссылки на другие файлы, секреты, тесты, копии и временные материалы по своим правилам.
  5. Объединяет локальные CSS-импорты верхнего уровня. Порядок правил сохраняется, пути к изображениям пересчитываются. JS и CSS не сжимаются автоматически.
  6. По необязательному флагу --api-url-from-env читает адрес API из указанной переменной и записывает публичный env.js.
  7. Проверяет результат, заменяет свою .public/ и записывает отметку .public-build.json.

В адресе API запрещены логин/пароль, параметры после ? и фрагмент после #. Относительный адрес должен начинаться с одного /, например /api.

Список разрешённых имён включает index.html, 404.html, env.js, .nojekyll, robots.txt, sitemap.xml и значок сайта. Это список допуска. Сборщик не создаёт robots.txt и sitemap.xml сам.

Если непустая .public/ не имеет правильной отметки сборщика, замена остановится. Сначала выясните, что лежит в папке. Подделывать отметку для обхода проверки не нужно. Старый результат удаляется при замене, поэтому этот способ не гарантирует обновление без перерыва.

Пример записи отдельного адреса API, Windows PowerShell:

$env:API_URL = 'https://api.example.kz/api'
python deploy/prepare_frontend.py --api-url-from-env API_URL

Замените учебный адрес настоящим. В Docker-схеме сайт и API работают на одном домене: Nginx подставляет deploy/env.js со значением /api. На Render адрес записывает команда сборки из render.yaml. В Pages публикуется демо с пустым API и своим расширением.

Как Nginx направляет запросы

Nginx — внешний вход в магазин. Обычный HTTP перенаправляется на HTTPS, кроме пути проверки сертификата ACME. Адрес с www приводится к основному домену, неизвестное имя хоста отклоняется.

Кеш — сохранённая копия файла, чтобы не загружать его заново. Nginx разрешает кешировать файлы оформления и скрипты до 7 дней, фото media — до 30 дней. Как обновить работающий сервер

Следующие команды — Bash на Linux VPS, из корня проекта. Перед ними сохраните копии базы и media по главе 13, запишите текущую версию кода и прочитайте новые миграции. Во время обновления активные запросы могут прерваться.

git rev-parse HEAD
git pull --ff-only
python3 deploy/prepare_frontend.py
docker compose --env-file deploy/.env -f deploy/docker-compose.yml config --quiet
docker compose --env-file deploy/.env -f deploy/docker-compose.yml build backend
docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm --no-deps backend python -m app.cli check
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d
docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps

Что ожидать: Git покажет старую версию и получит изменения; сборщик обновит витрину; Compose проверит настройки, соберёт API и запустит сервисы. При запуске backend автоматически выполнит миграции. Последняя команда покажет состояние контейнеров. Если один шаг завершился ошибкой, сначала разберите её, прежде чем переходить к следующему.

После запуска откройте HTTPS-сайт и /api/health, проверьте вход, каталог, фото и ранее созданный заказ. Если меняли конфигурацию Nginx, проверьте её и примените:

docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec web nginx -t
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec web nginx -s reload

Выполняйте reload только после успешного nginx -t. При смене DOMAIN или окружения web его нужно пересоздать, чтобы шаблон получил новые значения. Автоматическое применение миграций не делает любую будущую миграцию безопасной: до запуска проверяются её изменения и резервная копия.

Резервные копии и восстановление

Backup делает первую попытку сразу, затем примерно раз в сутки. Успешная пара файлов выглядит как kbch-ДАТА.dump и media-ДАТА.tgz: база и фотографии. При сбое временные файлы удаляются, старые копии сохраняются.

База и фото копируются последовательно. Это не один одновременный снимок: учитывайте фото, загруженные между этими операциями. Срок хранения задаёт BACKUP_KEEP_DAYS, по умолчанию 14 дней.

Копии в deploy/backups/ находятся на том же сервере. Для защиты от его потери переносите их также в другое место. Облачное копирование и проверка его успеха в Compose не настроены. Просматривайте журнал backup и периодически проверяйте восстановление в отдельной среде.

Порядок восстановления базы и media и отката описан в главе 14. Возврат старого кода не возвращает автоматически прежнюю схему и данные. Команда docker compose down -v удаляет постоянные тома, в том числе базу, фото и сертификаты; это не команда обычного обновления.

Чем отличаются Render и GitHub Pages

render.yaml описывает PostgreSQL, API с постоянным диском и статическую витрину. Nginx, Certbot и backup из Compose там не запускаются. Соответствующие функции и копии нужно настраивать средствами хостинга. Планы в YAML — параметры репозитория; их доступность и стоимость проверяются в панели перед заказом.

GitHub Pages публикует только demo/.public/. Настоящий Python API и PostgreSQL там не запускаются. Аккаунты, заказы и имитация оплаты демо находятся в браузере. Подробнее — глава 15.

Эта глава нужна разработчику, который продолжит работу над магазином. Если нужно только добавлять товары, обрабатывать заказы и менять фотографии, начните с главы 11 и главы 12.

Перед изменением

  1. Запустите нужный режим по главе 2.
  2. Уточните, где сейчас данные: в браузере, локальном API или на рабочем сервере.
  3. Найдите нужные файлы по главе 22.
  4. Проверьте действие до правки, чтобы понимать исходное поведение.
  5. Меняйте исходники. Для витрины это frontend/, для API — backend/. Готовую .public/ получают повторной сборкой.

Библиотеки устанавливайте в отдельное Python-окружение проекта. Рабочие данные покупателей и настоящие секреты не нужны для написания документации и обычной локальной проверки. README и docs описывают код в этой папке; они не подтверждают настройки какого-либо отдельного сервера.

Как добавить страницу

Возьмите существующую HTML-страницу с таким же уровнем вложенности и используйте её как основу. Например, для файла в pages/ ориентируйтесь на другую страницу из pages/.

  1. Задайте своё значение data-page и правильный путь data-base.
  2. Добавьте страницу в список PAGES в frontend/js/app.js. Сначала подключаются тексты и вспомогательные файлы, затем логика страницы.
  3. Учитывайте событие app:ready: оно сообщает, что приложение подготовлено. При изменении данных используйте принятые в проекте события.
  4. Подключите CSS через frontend/css/main.css, правила для экранов — через frontend/css/responsive/index.css.
  5. Добавьте нужные ссылки в навигацию и карту документации.
  6. Проверьте страницу прямым открытием адреса и переходом с другой страницы.

Для нового языка недостаточно скопировать texts/ru/: нужно перевести все используемые ключи, указать правильный lang в HTML и проверить форматирование и серверные ошибки. Готового переключателя языка в текущем магазине нет.

Как изменить структуру базы

Модель описывает таблицу в коде. Миграция описывает, как изменить уже существующую базу. Нужны обе части: изменение только models.py не обновит рабочую базу само.

Работайте с отдельной базой разработки, управляемой Alembic. Не используйте базу с реальными заказами. Подготовьте адрес этой базы в настройках, перейдите в backend и активируйте нужное окружение.

Последовательность:

  1. Выполните alembic upgrade head, чтобы база соответствовала текущей истории миграций.
  2. Измените backend/app/db/models.py.
  3. Создайте миграцию и прочитайте полученный файл.
  4. Примените её и проверьте, нет ли различий между моделями и базой.

Команды для шагов 3–4, из backend с активным окружением:

alembic revision --autogenerate -m "add_product_field"
alembic upgrade head
alembic check

add_product_field — пример короткого описания; замените его названием своего изменения. Автогенерация не всегда понимает переименование. Она может предложить удалить старую колонку и добавить новую, потеряв значения. Автор должен продумать перенос данных и прочитать миграцию перед применением.

Локальная база, созданная автоматически через create_all, может не иметь истории Alembic. Для работы над миграциями удобнее создать отдельную пустую базу и применить к ней всю историю. Если новое поле обязательно, заранее решите, чем заполнить его у существующих записей.

В GitHub проверяются upgrade, check и downgrade base на одноразовом PostgreSQL. Откат до base там нужен для теста. Он не является инструкцией очищать рабочую базу.

Команды тестов собраны в главе 16. Выбирайте проверки по тому, что изменилось. Для серверных расчётов нужны тесты запросов и сценария заказа; для надписи — правильный ключ и просмотр страницы. Тесты логики JS не показывают, удобно ли нажимается кнопка на телефоне.

Как оформлять команды и примеры

Над блоком команд укажите систему и папку запуска. powershell — Windows, bash — Linux/macOS или VPS. Пути к Python-окружению отличаются: Windows — backend/.venv/Scripts/python.exe, Linux/macOS — backend/.venv/bin/python.

cd backend меняет текущую папку: последующие команды выполняются из неё. Многоточие в объяснении означает пропущенную часть и не должно появляться в команде для копирования.

example.com, example.kz, p-example и <домен> — заполнители. Объясняйте рядом, чем их заменить. API_URL публичен; SECRET_KEY, пароли и токены — секреты. Настоящие секреты передаются через локальное окружение, защищённый .env или панель хостинга.

Какие ограничения уже есть

Магазин — набор отдельных страниц, которые JavaScript заполняет данными, и API на FastAPI. Сейчас нет общей корзины между устройствами, серверной выдачи каталога порциями, общего Redis-хранилища лимитов, автоматического банковского возврата, полного набора браузерных тестов или гарантии обновления без перерыва. Учитывайте эти границы при обещании новых функций.

27 Архитектура как части магазина работают вместе

Эта глава нужна разработчику, чтобы выбрать правильное место для изменения и не смешать разные задачи в одном файле. Архитектура — способ разделить программу на понятные части. Для работы с товарами через админку эту главу можно пропустить.

У магазина две основные части: браузер показывает страницы и принимает действия, Python API проверяет запросы и работает с базой. На сервере используется PostgreSQL. Для простого локального запуска и части тестов — SQLite, база в одном файле.

Пример покупатель оформляет заказ

  1. Страница в браузере собирает контакты, товары и количество.
  2. Клиентский слой хранилища отправляет запрос API.
  3. Схема проверяет поля: есть ли имя, допустимо ли количество, не слишком ли длинный текст.
  4. Обработчик API проверяет вход пользователя, наличие товаров и остатки, считает сумму.
  5. Сервис оплаты готовит нужные инструкции.
  6. База сохраняет заказ и изменение остатков.
  7. Сериализатор превращает запись базы в JSON-ответ, который браузер показывает покупателю.

Это разделение называется послойной архитектурой: у каждого слоя своя задача. В этом проекте часть правил заказа находится прямо в обработчике. Отдельного сервиса для каждого действия и отдельного слоя репозиториев нет.

Как запускается API

Все пути следующей таблицы отсчитываются от backend/.

При обычном Docker-запуске entrypoint.sh сначала проверяет конфигурацию, затем выполняет миграции, затем запускает Gunicorn с Uvicorn-процессами. Встроенное создание таблиц относится к локальной SQLite и не заменяет этот порядок на сервере.

Схема проверяет форму запроса, но не выполняет SQL-запросы. Модель описывает таблицу, но не знает об адресе HTTP. Общая настройка читается из Settings, а не придумывается внутри обработчика одной страницы. Такое разделение помогает менять одну часть без лишних изменений остальных.

Как устроена оплата

В app/services/payments/base.py описан общий интерфейс платёжного способа — какие действия он должен уметь. Конкретные реализации находятся в cash.py, kaspi_transfer.py, sandbox.py и kaspi_pay.py. Список в payments/__init__.py выбирает включённые и настроенные методы.

Для нового провайдера нужно реализовать его правила, добавить метод в список, подключить настройки и проверить создание заказа, инструкции, статусы и уведомления. Адрес и формат внешнего API подтверждаются по условиям провайдера. Наличие реализации в коде не подтверждает боевое подключение.

Команда предполагает, что окружение и зависимости уже подготовлены. Тесты создают временную базу, заменяют отправку писем и внешние платёжные запросы. Они проверяют код без реального списания денег и реальной почтовой доставки. Команды остальных проверок находятся в главе 16.

Если менялась структура таблиц, подготовьте миграцию и проверьте её на отдельной базе. Если менялся интерфейс, просмотрите нужное действие в браузере. Подробный порядок разработки — глава 26.

Требования к фотографиям оформления

Этот список нужен, если вы хотите заменить фотографии на страницах сайта: первый экран, «О нас», доставку и вход. Его можно передать фотографу или дизайнеру. Фото товаров сюда не входят: их загружают через админку.

Главное правило

Каждую новую картинку сохраняют точно по указанному пути, с тем же именем, форматом и размером, заменяя старый файл. Код сайта менять не нужно: картинки подставятся сами.

Общий стиль для всех фото

  • Настроение: спокойная природная эстетика, «аптекарский сад»: чистота, забота, натуральность, премиальность без пафоса.
  • Свет: мягкий тёплый дневной, рассеянный, лёгкие тени от листьев. Без резких бликов, неона и студийного белого фона.
  • Палитра: тёплый кремовый и песочный (#F3EFE6, #ECE7DB), глубокий лесной зелёный (#1F3A2D), шалфей (#9DAE8C), натуральный камень, светлое дерево, керамика. Акценты — белые цветы (жасмин, ромашка).
  • Предметы: стеклянные флаконы и баночки без надписей и логотипов, ракушечник и травертин, листья эвкалипта, центеллы, оливы, сушёные травы и цветы, льняная ткань, керамические пиалы.
  • Нельзя: текст, буквы, логотипы и бренды на упаковке, водяные знаки, люди с лицами (допустимы руки), пластиковые мусорные детали, перенасыщенные цвета, искажённые руки и предметы.
  • Качество: фотореализм, глубина резкости как у полнокадровой камеры 50–85 мм, ровный горизонт.
  • Сжатие: JPG — качество 82–85, прогрессивный, без EXIF. Ориентир размера — в таблице. PNG и WebP — с прозрачным фоном там, где указано.

Декоративные веточки по желанию

Файлы в assets/images/decor/: PNG с прозрачным фоном, не больше 1100 px по большей стороне, до 700 КБ каждый. На сайте они маленькие (до 280 px) и висят по краям страниц. Нужны отдельные растения без земли и горшков, с аккуратным краем: aloe-stones.png (алоэ на камешках), branch-right.png (ветка, растущая справа), centella-leaves.png (листья центеллы), chamomile-sprig.png (вертикальная веточка ромашки), eucalyptus-round-spray.png (круглолистный эвкалипт), jasmine-divider.png (горизонтальная ветка жасмина, вытянутая 3:1), tea-branch.png (ветка чайного куста).

Проверка после замены

  1. Из корня проекта выполните python deploy/serve_frontend.py и откройте http://localhost:5174.
  2. Проверьте главную, «О нас», «Доставка и оплата», «Вход» на ширине 390 px (телефон) и 1440 px (компьютер):
  • текст на первом экране и надпись на фото доставки читаются;
  • в мозаике «Жизнь магазина» ничего важного не обрезано;
  • нет ни одного слова, логотипа или водяного знака на фото.
  1. Вес каждого файла — не больше указанного в таблице.

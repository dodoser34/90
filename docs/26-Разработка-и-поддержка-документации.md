# 26. Как изменять проект и документацию

Эта глава нужна разработчику, который продолжит работу над магазином. Если нужно только добавлять товары, обрабатывать заказы и менять фотографии, начните с [главы 11](11-Админ-панель.md) и [главы 12](12-Тексты-фото-и-частые-правки.md).

## Перед изменением

1. Запустите нужный режим по [главе 2](02-Как-запустить.md).
2. Уточните, где сейчас данные: в браузере, локальном API или на рабочем сервере.
3. Найдите нужные файлы по [главе 22](22-Карта-папок-и-файлов.md).
4. Проверьте действие до правки, чтобы понимать исходное поведение.
5. Меняйте исходники. Для витрины это `frontend/`, для API — `backend/`. Готовую `.public/` получают повторной сборкой.

Библиотеки устанавливайте в отдельное Python-окружение проекта. Рабочие данные покупателей и настоящие секреты не нужны для написания документации и обычной локальной проверки. README и docs описывают код в этой папке; они не подтверждают настройки какого-либо отдельного сервера.

## Где менять нужную функцию

| Задача | Где править | Что проверить после |
|---|---|---|
| Изменить надпись или описание страницы | `frontend/texts/ru/` | Нужный ключ, переносы и вид на телефоне |
| Изменить цвет, шрифт, ширину | `frontend/css/base/variables.css` и CSS нужного блока | Читаемость, выбор клавиатурой, телефон и широкий экран |
| Изменить корзину | `frontend/js/store/cart.js` и связанные компоненты | Количество, недоступные товары и JS-тесты |
| Добавить поле товара | Форма админки, store/products, schemas/catalog, сериализатор; при отдельной колонке также модель базы | Сохранение и чтение API, старые товары, локальный режим |
| Добавить страницу | HTML, тексты, CSS, JS и PAGES в app.js | Адреса файлов, запуск логики, ссылки и доступ |
| Добавить таблицу или колонку | models.py, миграция, схемы и обработчики | Старые данные, SQLite и PostgreSQL, применение миграций |
| Добавить адрес API | Обработчик в router, схема полей, права; при необходимости remote.js | Токен, роль, неверные данные и ошибки |
| Добавить настройку сервера | Settings, образец .env; при необходимости Compose/Render | Значение при отсутствии, production-проверки и описание |
| Добавить оплату | services/payments, список методов, Settings; при необходимости webhook | Контракт провайдера, сумму, подпись, повтор и отказ |

Имена backend-папок в таблице относятся к `backend/app/`, если не указан другой путь. «Сериализатор» — код, который переводит запись базы в JSON-ответ браузеру.

## Как добавить страницу

Возьмите существующую HTML-страницу с таким же уровнем вложенности и используйте её как основу. Например, для файла в `pages/` ориентируйтесь на другую страницу из `pages/`.

1. Задайте своё значение `data-page` и правильный путь `data-base`.
2. Добавьте страницу в список PAGES в `frontend/js/app.js`. Сначала подключаются тексты и вспомогательные файлы, затем логика страницы.
3. Учитывайте событие `app:ready`: оно сообщает, что приложение подготовлено. При изменении данных используйте принятые в проекте события.
4. Подключите CSS через `frontend/css/main.css`, правила для экранов — через `frontend/css/responsive/index.css`.
5. Добавьте нужные ссылки в навигацию и карту документации.
6. Проверьте страницу прямым открытием адреса и переходом с другой страницы.

Для нового языка недостаточно скопировать `texts/ru/`: нужно перевести все используемые ключи, указать правильный `lang` в HTML и проверить форматирование и серверные ошибки. Готового переключателя языка в текущем магазине нет.

## Как изменить структуру базы

**Модель** описывает таблицу в коде. **Миграция** описывает, как изменить уже существующую базу. Нужны обе части: изменение только models.py не обновит рабочую базу само.

Работайте с отдельной базой разработки, управляемой Alembic. Не используйте базу с реальными заказами. Подготовьте адрес этой базы в настройках, перейдите в `backend` и активируйте нужное окружение.

Последовательность:

1. Выполните `alembic upgrade head`, чтобы база соответствовала текущей истории миграций.
2. Измените `backend/app/db/models.py`.
3. Создайте миграцию и прочитайте полученный файл.
4. Примените её и проверьте, нет ли различий между моделями и базой.

Команды для шагов 3–4, из `backend` с активным окружением:

```bash
alembic revision --autogenerate -m "add_product_field"
alembic upgrade head
alembic check
```

`add_product_field` — пример короткого описания; замените его названием своего изменения. Автогенерация не всегда понимает переименование. Она может предложить удалить старую колонку и добавить новую, потеряв значения. Автор должен продумать перенос данных и прочитать миграцию перед применением.

Локальная база, созданная автоматически через create_all, может не иметь истории Alembic. Для работы над миграциями удобнее создать отдельную пустую базу и применить к ней всю историю. Если новое поле обязательно, заранее решите, чем заполнить его у существующих записей.

В GitHub проверяются upgrade, check и downgrade base на одноразовом PostgreSQL. Откат до base там нужен для теста. Он не является инструкцией очищать рабочую базу.

## Как проверить результат

Команды тестов собраны в [главе 16](16-Тесты-и-проверка-качества.md). Выбирайте проверки по тому, что изменилось. Для серверных расчётов нужны тесты запросов и сценария заказа; для надписи — правильный ключ и просмотр страницы. Тесты логики JS не показывают, удобно ли нажимается кнопка на телефоне.

В инструментах разработчика браузера полезны следующие вкладки:

| Вкладка | Что показывает |
|---|---|
| Console | Ошибки JavaScript |
| Network | Неудачные загрузки файлов и запросы к API |
| Application | Память localStorage и другие данные сайта |
| Режим устройств | Как страница выглядит при другой ширине экрана |

Записывайте проверенный сценарий и результат. Например: «Добавил товар с двумя фото, сохранил, открыл на телефоне, обе фотографии доступны». Отчёт должен описывать выполненную проверку, без обещаний о непроверенных устройствах и браузерах.

## Что обновлять в документации

| Что изменилось | Какие главы просмотреть |
|---|---|
| Папка, модуль или страница | 3, профильная глава 4/6/7 и карта 22 |
| Библиотека или версия Python/Node | 7 и 20 |
| Конфигурация или автоматическая проверка | 16 и 21 |
| Переменная Settings или Compose | 13 и 23 |
| Поле API, статус, адрес или права | 7 и 24 |
| Сборка, сервер или копии | 13, 14 и 25 |
| Действие пользователя | 1, 11/12 и вопросы 17 |
| Разделение ответственности между частями | 3 и 27 |

Описывайте то, что делает текущий код. Если связь с внешним сервисом ещё не проверена, укажите это прямо. Например: «Адаптер отправляет такие поля; работу с боевым провайдером ещё нужно подтвердить».

## Как оформлять команды и примеры

Над блоком команд укажите систему и папку запуска. `powershell` — Windows, `bash` — Linux/macOS или VPS. Пути к Python-окружению отличаются: Windows — `backend/.venv/Scripts/python.exe`, Linux/macOS — `backend/.venv/bin/python`.

`cd backend` меняет текущую папку: последующие команды выполняются из неё. Многоточие в объяснении означает пропущенную часть и не должно появляться в команде для копирования.

`example.com`, `example.kz`, `p-example` и `<домен>` — заполнители. Объясняйте рядом, чем их заменить. API_URL публичен; SECRET_KEY, пароли и токены — секреты. Настоящие секреты передаются через локальное окружение, защищённый `.env` или панель хостинга.

## Какие ограничения уже есть

Магазин — набор отдельных страниц, которые JavaScript заполняет данными, и API на FastAPI. Сейчас нет общей корзины между устройствами, серверной выдачи каталога порциями, общего Redis-хранилища лимитов, автоматического банковского возврата, полного набора браузерных тестов или гарантии обновления без перерыва. Учитывайте эти границы при обещании новых функций.

## Как проверить саму документацию

Проверьте ссылки между главами, существование названных файлов, версии requirements, все поля Settings, адреса API и команды запуска. Из корня проекта выполните:

```powershell
git diff --check
```

Команда выявляет часть проблем с пробелами в изменённых файлах. Правильность объяснений и верстку она не оценивает. При подготовке Word/PDF отдельно просмотрите готовый документ: заголовки, таблицы, переносы, блоки команд и ссылки.

После правок глав пересоберите руководство из корня проекта:

```powershell
python docs/tools/build_guide.py
```

Для сборки нужна библиотека `python-docx`. Проверьте оба результата: файл Word и браузерную версию. Убедитесь, что текст читается на компьютере и телефоне, таблицы помещаются, а команды и ссылки отображаются без лишних символов.

Если тесты или просмотр были выполнены, укажите дату, команду, среду и результат. Время работы тестов, их число и внешние тарифы могут измениться. Старое сообщение «все тесты проходят» нельзя автоматически переносить на новую версию кода.

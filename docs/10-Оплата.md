# 10. Оплата

## Главное: какие способы действительно принимают деньги

**Перевод на Kaspi** показывает реквизиты владельца. Покупатель переводит деньги самостоятельно, а владелец проверяет поступление и вручную отмечает оплату.

**Оплата при получении** означает расчёт с курьером или при самовывозе. Магазин сам организует приём денег. Наличие способа в коде не выдаёт курьеру банковский терминал.

**Тестовая карта и тестовый Kaspi** только показывают процесс. Денег они не списывают, даже если заказ после проверки получил статус «Оплачен».

**Kaspi Pay** представлен в коде отдельным адаптером — частью для связи с платёжным провайдером. Его боевой адрес, форматы и правила ещё нужно сверить с условиями доступного вам сервиса и проверить. Готовность к реальному приёму денег не подтверждена самим наличием адаптера.

## Где включаются способы оплаты

При размещении через Docker Compose откройте `deploy/.env` на сервере. Строка ниже — **настройка файла, а не команда PowerShell**:

```env
PAYMENT_METHODS=kaspi_transfer,cash,test_card,test_kaspi
```

Имена разделяются запятыми. Покупателю показываются только включённые способы с заполненными обязательными настройками.

| Код в настройке | Способ | Обязательные поля |
|---|---|---|
| `kaspi_transfer` | Перевод на Kaspi | `KASPI_PHONE`, `KASPI_RECEIVER` |
| `cash` | При получении | Дополнительных полей нет |
| `test_card` | Имитация оплаты картой | Дополнительных полей нет |
| `test_kaspi` | Имитация оплаты через Kaspi | Дополнительных полей нет |
| `kaspi_pay` | Адаптер Kaspi Pay | `KASPI_MERCHANT_ID`, `KASPI_API_KEY`, `KASPI_WEBHOOK_SECRET`; также нужна проверка контракта |

Готовность настроек видна в админ-панели: **Настройки → Готовность к запуску**. Из терминала можно запустить `app.cli check` по [разделу 7](07-Бэкенд-Python.md). В рабочем режиме сервер откажется запускаться, если включён неизвестный способ или не хватает его обязательных полей.

После изменения `deploy/.env` примените настройки из папки проекта на сервере:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d backend
```

Затем обновите страницу оформления и проверьте список способов. Если используется другой хостинг, меняйте его переменные окружения и перезапускайте сервис по инструкции этого размещения.

## Перевод на Kaspi: действия владельца

В `deploy/.env` укажите настоящие реквизиты. Пример ниже содержит вымышленные данные:

```env
KASPI_PHONE=+7 700 123 45 67
KASPI_RECEIVER=Имя получателя
KASPI_PAY_LINK=
```

`KASPI_PHONE` — номер для перевода, `KASPI_RECEIVER` — имя получателя, которое должен увидеть покупатель. Необязательное поле `KASPI_PAY_LINK` — ссылка для перехода к оплате, если она у вас есть. Пустое значение оставляет перевод по номеру.

1. Покупатель оформляет заказ и видит номер, имя получателя, сумму и комментарий вида «Заказ №1001».
2. Заказ получает статус оплаты «Ждёт оплаты». Инструкция также доступна в личном кабинете.
3. Покупатель переводит деньги в своём приложении.
4. Владелец проверяет поступление по своим операциям, открывает заказ в админ-панели и выбирает **Оплата → Оплачен**.

Сайт не проверяет банковский перевод автоматически. Сообщение или снимок экрана от покупателя сами по себе не меняют статус.

В локальном режиме вместо настоящих реквизитов подставлены `+7 700 000 00 00` и «Магазин (тест)». Не используйте их для настоящей оплаты.

## Оплата при получении

Дополнительные ключи не нужны. Заказ получает статус оплаты «При получении». После расчёта владелец вручную отмечает «Оплачен».

Текст интерфейса допускает карту через терминал курьера. Показывайте это обещание покупателю только если приём карт действительно организован. Сам сайт терминал и банковский эквайринг не подключает.

## Как проверить тестовую оплату

Сначала оформите заказ с сервером и выберите тестовую карту или тестовый Kaspi. Сайт откроет `pages/pay.html?order=…`. Позже к этой странице можно вернуться из личного кабинета кнопкой «Перейти к оплате».

**Для карты** используйте примеры из таблицы, будущий срок, например `12/30`, и CVC `123`. CVC — короткий проверочный код карты; в тесте это вымышленные цифры.

| Номер тестовой карты | Результат |
|---|---|
| `4242 4242 4242 4242` | Успешная имитация оплаты |
| `4000 0000 0000 0002` | Сообщение об отклонении, статус «Не прошла» |
| `4000 0000 0000 9995` | Сообщение «Недостаточно средств» |

На странице есть кнопки подстановки тестовых значений. Сервер проверяет математическую корректность номера по алгоритму Луна, формат срока и CVC. Это проверка формы данных, **не обращение в банк**. Полный номер и CVC в заказе не сохраняются; остаются последние четыре цифры в подписи тестовой оплаты. Вводить настоящую карту не нужно.

**Для тестового Kaspi** откройте имитацию приложения со страницы оплаты и нажмите «Подтвердить оплату» или «Отменить». QR-код и экран здесь являются частью показа, а не подключением к приложению банка.

После успеха статус заказа станет «Оплачен» в кабинете и админ-панели. Такой заказ учитывается как оплаченный внутри магазина, хотя денег не было. Поэтому проверочные заказы нужно отличать от настоящих при разборе продаж.

### Что ограничено

Оплатить тестом можно только свой заказ с выбранным тестовым способом. Повторная оплата уже оплаченного или возвращённого заказа запрещена. Отменённый заказ оплатить нельзя. После удаления `test_card` и `test_kaspi` из `PAYMENT_METHODS` тестовая оплата перестаёт работать.

Перед приёмом реальных заказов уберите тестовые способы. Пример для ручных расчётов:

```env
PAYMENT_METHODS=kaspi_transfer,cash
```

## Статус заказа и статус оплаты — разные поля

Статус заказа описывает обработку и доставку: новый, в работе, отправлен, завершён или отменён. Статус оплаты описывает деньги:

| Статус оплаты | Что означает |
|---|---|
| При получении | Расчёт ожидается при передаче заказа |
| Ждёт оплаты | Способ выбран, подтверждения ещё нет |
| Оплачен | Заказ отмечен оплаченным; для тестового способа это результат имитации |
| Не прошла | Платёжная попытка отклонена или отменена |
| Возврат | В учёте отмечен возврат |

Изменение статуса на «Возврат» само не отправляет деньги покупателю. Фактический возврат нужно провести выбранным способом отдельно.

Сумму заказа рассчитывает сервер по ценам базы. Сумма из формы браузера не является источником для списания.

## Технические подробности: подключение Kaspi Pay

Этот подраздел нужен разработчику. До включения адаптера получите договор и документацию доступного платёжного сервиса. Проверьте, что вам действительно выданы нужные доступы: их получение и совместимость текущего кода не гарантированы.

В `backend/app/services/payments/kaspi_pay.py` реализован следующий ожидаемый контракт:

- `start()` отправляет запрос на `<KASPI_API_URL>/invoices` с Bearer-ключом. Передаются `merchantId`, `orderId`, целая сумма в тенге, `currency`, описание, адрес возврата и адрес уведомления.
- Ответ должен содержать идентификатор счёта и ссылку HTTPS на оплату; поддержаны имена `invoiceId`/`id` и `paymentUrl`/`url`.
- Адрес уведомлений: `https://ВАШ-ДОМЕН/api/payments/kaspi/webhook`. **Webhook** — автоматическое сообщение платёжного сервиса вашему серверу.
- `check_signature()` проверяет HMAC-SHA256 исходного тела сообщения с секретом; подпись ожидается в заголовке `X-Signature`.
- `parse_webhook()` разбирает `orderId`, `status` и целую сумму `amount`.

Адрес, авторизация, поля и подпись должны точно соответствовать реальному провайдеру. До подтверждения совместимости не включайте `kaspi_pay` покупателям. Подробный формат текущей реализации — [раздел 24](24-API-и-форматы-данных.md).

В обработчике уведомлений неверная подпись отклоняется. Для сообщения об успехе сумма сверяется с заказом. Повторное сообщение для уже оплаченного или возвращённого заказа не меняет его снова. При выключенном `kaspi_pay` адрес уведомления возвращает 404.

После сверки и доработки настройте `KASPI_API_URL`, `KASPI_MERCHANT_ID`, `KASPI_API_KEY`, `KASPI_WEBHOOK_SECRET`, адреса сайта и API. Проведите проверки в среде провайдера, затем контролируемую проверку реального расчёта по согласованной процедуре.

## Технические подробности: файлы и новый способ

Способы находятся в `backend/app/services/payments/`: `cash.py`, `kaspi_transfer.py`, `sandbox.py`, `kaspi_pay.py`. Общие правила — в `base.py`, список способов `METHODS` — в `__init__.py`.

Разработчик добавляет отдельный класс способа с кодом, заголовком, требованиями к настройкам, запуском `start()` и инструкцией `instructions()`. Затем регистрирует его в `METHODS`, добавляет поля в `backend/app/core/config.py` и тесты его реального контракта. Для автоматических уведомлений нужен обработчик с проверкой подписи, суммы и повторов.

Сайт уже получает список способов от сервера. Существующий формат инструкции может подойти без новых элементов страницы; иной платёжный сценарий потребует доработки интерфейса. Простого копирования файла старого провайдера недостаточно для безопасного подключения нового.

Тестовый обработчик расположен в `backend/app/api/routers/orders.py`, проверка карты — в `sandbox.py`, интерфейс — в `frontend/pages/pay.html`, `frontend/js/pages/pay.js` и `frontend/css/pages/pay.css`.
